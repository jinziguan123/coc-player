# 移动领域边界

更新日期：2026-10-25。

本轮把移动的个人检定与共同障碍结算，从数据库驱动的流程中抽出。目标是让业务规则能以普通值测试，避免每次修改结算语义都需要准备 ORM 和模型替身。

## 当前职责

| 位置 | 负责什么 |
|---|---|
| `app/domain/movement.py` | 不可变移动意图、通行裁定、检定结果与结算决策；个人通行、共同障碍、重复结果与参与者资格规则 |
| `app/domain/movement_language.py` | 移动原话分类与出口词识别，不读取模组或存档 |
| `app/domain/movement_space.py` | 只读空间快照与出口目的地解析，歧义时返回候选而不擅自选择 |
| `app/domain/movement_party.py` | 依据参与者快照选择跟随者、工具默认带头人及规划器提案带头人，维护真人自主行动与独行边界 |
| `app/domain/movement_evidence.py` | 原话与规划器的行动证据门槛，决定忽略、停止裁定或继续解析出口 |
| `app/application/movement_space.py` | 将模组 JSON 字段投影为不可变快照，避免保留 ORM 或可变 JSON 引用 |
| `app/application/movement_plans.py` | AI `TurnPlan` 到领域 `MovementIntent` 的转换，兼容旧 `scene_change` |
| `app/application/movement_execution.py` | 裁定结果装配、批次提交用例及写入端口；同事务暂存移动与回合状态，提交后返回凭据 |
| `app/domain/checks.py` | 检定通用规则：技能名归一与匹配（`check_gating.skill_matches` 为兼容导出） |
| `app/application/movement_settlement.py` | 检定落地时的门控移动批次结算：按技能匹配逐条结算，产出移动命令与类型化状态更新 |
| `app/application/movement_adjudication.py` | 单条及批次裁定编排，使用参与者快照和只读导航端口，返回角色 ID 裁定 |
| `app/application/movement_state.py` | 待检定移动与回合裁定记录的类型化读取、旧存档兼容和个人状态写回，保留未处理字段；存档 JSON 键只在此处与原服务的兼容入口出现 |
| `app/services/movement.py` | 原有公开入口、导航候选集适配、状态加载、位置资格快照、事务写入和提交后的展示 |

调用方向：原移动服务使用输入转换器取得领域意图，使用领域函数计算结算结果，再执行位置和事件写入。领域只接收角色 ID、状态和结果，不接收 SQLAlchemy Session、ORM 对象、Provider 或事件推送对象。

`settle_check` 不修改传入状态；返回的状态和角色名单以不可变元组承载。执行顺序沿用原提案顺序。参与者是否仍在出发位置由应用服务提供快照，领域规则根据资格集合决定是否允许移动。共享障碍成功时包含先前尝试失败的参与者；个人检定只允许成功者通过。

## 兼容与事务

存档键、状态字符串、接口与重生成策略不变，无需迁移数据库或重新导入模组。模型容错仍由 AI 层负责，领域不重复实现模型输出修复。

移动批次用例通过写入端口统一控制事务范围，原移动服务的适配器提供现有数据库事务实现：位置、事件、待执行记录和裁定凭据一起提交；广播和配图仍在提交之后。

## 约束与验证

`test_layering.py` 新增领域依赖禁令，包含函数内导入；领域仅允许标准库及领域模块，禁止通过相对导入越过领域目录。

`test_movement_space.py` 检查多出口歧义、方位选择、别名解析、快照隔离与原话分类。

`test_movement_domain.py` 检查个人/共享结果差异、先失败后成功、离场参与者、全员失败、重复与无关结果，以及规划器转换的兼容性。原 `test_natural_movement.py` 继续验证真实编排、工具入口和数据库事务。

## 尚未迁移

这不是完整的六边形架构迁移。原话分类、空间解析、参与者选择和行动证据门槛已迁入领域，移动服务仍承担角色名字匹配、导航适配、剩余裁定编排、ORM 和展示；没有新增通用仓储接口或 Unit of Work 框架。`services` 内原有的循环依赖也尚未全部解除。

后续应按业务收益继续分离剩余移动裁定，再明确持久化和输出端口；不应仅为缩小文件而把同一套依赖复制到更多文件。其他模块不应反向引用领域以外的实现来扩展本领域。

## 第二轮：空间解析

空间快照只包含场景 ID、称谓、描述、出口与候选 ID，所有嵌套集合均使用 tuple/frozenset。
构建后修改源模组 JSON 不会改变快照。领域解析只负责判定文字指向哪个目的地，不负责授权移动。
连通图、可通行限制与地点类型仍由现有导航/场景服务提供并校验；没有复制或放宽原有通行规则。

旧的 `movement.analyze`、`movement.scene_terms`、`movement.resolve_destination` 调用入口保留，
原话分类和目的地解析的实现各只有一份。无数据库迁移或存档字段变化。

## 第三轮：参与者选择

服务层读取角色位置、控制权和本轮表态，并解析明确的个人去向，构建不可变的 `Participant` 快照。
领域函数只返回角色 ID，服务层再映射回现有角色对象；不在领域内查询数据库。
工具默认带头人和跟随者共用一组快照，避免重复解析同一角色的去向。

沉默真人不会被点名或房主默认跟随带走；独行、留守、不同位置、已有裁定和不同目的地仍优先排除。
工具默认带头人必须直接宣告行动，仅表态跟随的人不会成为带头人；原有回退角色语义保留。
`test_movement_party.py` 直接验证这些规则，原编排测试继续验证服务边界；无模组时快照保留未知去向，不调用空间解析。

## 第四轮：规划器带头人与行动证据

规划器点名后只在点名者中选择带头人，未点名才在全队中选择；排序仍然是行动表态优先、真人其次、同级保持原顺序。
所有点名者都没有表态时仍回退到第一个点名者，由证据门槛阻止无依据移动。
这与工具默认带头人的规则不同，因此保留两个明确的领域入口，不合并为带模式开关的通用排序器。

行动证据以原话优先：大地图前往交给专用入口；原话不构成行动时停止；原话构成行动但规划器未认可时仍停止。
只有两者都认可才解析出口。领域返回明确的 `ignore`、`stop`、`resolve` 决策，服务层执行分支，不读取 ORM 来判定证据。
`test_movement_evidence.py` 验证这些优先级；`test_movement_party.py` 补充点名范围、稳定排序和回退行为。
寻路、阻挡原因展示、检定需求和事务仍由原服务编排，状态字符串和对外入口不变。

## 第五轮：通行与检定需求

`assess_passage` 接收移动意图、导航返回的可达性和旧检定门控，返回不可变的 `PassageDecision`。
适用前提是行动证据成立、目的地已明确且不同于原处；这几项前置判断仍由服务编排。
规则优先级为：路径不可达 → 通道明确受阻 → 需要检定 → 允许移动。
明确受阻时不建立待检定移动，显式技能优先于旧门控，空白显式技能回退到旧门控。

领域不读取地图，也不复制导航算法。服务仍通过 `find_scene_path` 和可通行集合处理借道限制，
通过 `travel_blocker` 获取不可达的解释；终点的限制标记仍不会被直接当作通道受阻。
路径可达且通道无阻碍后，才选择跟随者并进入原有事务。存档状态、检定消费和广播顺序不变。
领域测试覆盖规则冲突与技能回退；编排测试验证“受阻且带检定”不会错误创建待检定移动。

## 第六轮：移动提交用例与写入端口

直接移动、规划器批次移动、检定结算三个入口统一调用 `commit_movement_batch`。
用例只接受角色 ID 命令和回合状态更新，通过 `MovementWriter` 暂存移动、保存状态、提交与刷新。
`_MovementWriter` 暂留原服务作为适配器，映射角色对象和存档键，并复用 `_stage_move`、
`_set_turn_state` 与现有事务实现；没有新增数据库连接或改变提交范围。

用例在事务退出成功并刷新后才返回展示凭据，调用者随后广播；无移动但有状态更新的批次也会提交，
例如检定失败时消费待执行记录。直接移动不传状态更新，不会覆盖回合记录。
裁定日志调整到提交后，避免回滚批次留下貌似成功的裁定日志。

`test_movement_execution.py` 用内存端口验证写入顺序、失败传播和空移动批次。
原数据库测试继续覆盖位置、留守固定、事件和裁定记录一起回滚，以及重试与配图失败。
结构测试禁止提交用例依赖 ORM 或服务层。状态记录仍沿用旧 dict 格式，尚未建立完整的类型化存档模型；
导航读取、裁定装配和展示适配也仍在原服务，本轮只建立提交侧边界。

## 第七轮：待检定移动状态快照

`PendingMove` 将待检定移动的参与者、原处、目标、技能、共享标志和个人状态读成明确字段。
检定结算与漏挂检定补齐共用此快照，旧记录缺少 `chars` 或其为空时仍按 `movers` 补为待检定。
修改个人状态返回新快照，写回保留原记录其他字段（包括未知扩展字段）；源记录及写回记录使用深拷贝隔离。
这是只读元数据加个人状态更新的兼容对象，不是允许任意编辑所有字段的完整聚合。

存档键与 JSON 结构保持不变，无需重新导入模组。`MovementStateUpdate` 仍接收兼容字典，
普通裁定记录、工具守卫及新待执行记录的创建尚未全部类型化，后续应沿同一边界推进。

## 第八轮：回合裁定记录读取模型

`MoveRecord` 把 `turn_moves` 里的一条裁定读成明确字段：整条状态、移动者 ID 与名字、原处、目标、
留守者名字、出口、技能、原因、线索和个人状态。`load_move_records` 按回合锚点筛选，
`busy_ids` 给出已有裁定者。以下入口改为共用这套解释，不再各自读字典：

- 检定结算 `settle_pending_moves`：用 `concerns` 找到建立该待检定移动的那条裁定，`with_states` 写回；
- 工具守卫 `tool_guard`：用 `status_of` 取每人状态、`names_of` 取被拒者名字；
- 裁定说明恢复 `_verdict_from_record`（重新生成复用记录时）、移动证据 `has_move_evidence`、`busy_ids`。

字段所有权：`with_states` 是唯一更新入口，合并个人状态并以领域 `rollup` 重算整条状态；
其他字段只读，写回从私有深拷贝恢复，未知扩展字段保留。未更新的记录逐字写回，
旧记录不会再被补上空的 `char_status`（之前结算会给所有记录加这个空键，读取语义相同）。
个人状态的对外含义由领域 `person_status` 给出（`tried` 与 `pending` 同为待检定），
与 `rollup` 放在一起，避免 tried 的语义在两处漂移。某人不在个人状态中时沿用整条状态。

`turn_records`、`char_status` 和 `busy_ids` 的签名与返回值不变，仍供外部调用；
`char_status` 改为委托 `MoveRecord.status_of`。应用边界的结构测试放宽为允许依赖领域模块，
仍禁止 ORM、服务层、AI 及相对导入。

`test_movement_state.py` 覆盖旧记录缺字段、个人状态与整条状态的优先级和重算、只更新部分人、
引用隔离、扩展字段保留、记录与待检定移动的对应、锚点筛选，以及已有裁定者不等于待检定名单。
`test_natural_movement.py` 新增两例：结算写回保留扩展字段且不改无关旧记录；工具守卫读取无个人状态的旧记录。
原有真实数据库的回滚与重试测试继续通过。

第八轮结束时仍未迁移的新建记录与写入格式，已在第九轮处理；见下节。

## 第九轮：状态更新改用类型化记录

`MovementStateUpdate` 现在接收 `MoveRecord` 与 `PendingMove` 元组，不再接收字典。
写入适配器 `_MovementWriter.save_state` 统一调用 `to_record` 编码并写入存档键；
用例与内存端口测试只看到快照，不知道 JSON 键。

两个快照新增 `new` 构造器：先按存档格式编码再读回，因此新建与“读取—更新—写回”共用一套键名与默认值。
`adjudicate_plan` 不再手写裁定记录与待执行条目：落位裁定带全员 `moved` 个人状态，
待检定裁定带全员 `pending` 与共同障碍标志，其他裁定两者都不写，与之前的手写格式逐字一致。
`Verdict.record` 只负责把角色对象映射成 ID 与名字后交给 `MoveRecord.new`。
`settle_pending_moves`、`pending_unissued` 与新裁定时保留的旧待执行条目，都经同一个 `_pending_moves` 读取。

兼容：存档键、状态字符串与字段取值不变，无需迁移或重新导入。唯一的输出差异是：
新裁定时保留下来的极旧待执行条目，如果缺少 `chars`，现在会按移动者补成 `pending` 后写回；
这与之前读取它时的默认解释相同，第七轮起检定结算写回也已经这样做。

结构测试允许 `movement_execution` 与 `movement_state` 互相依赖，二者仍只能依赖标准库与领域模块。
新增测试：两个构造器输出与旧手写格式逐字对照；数据库中待检定裁定写入的键集合与待执行条目逐字比对；
不移动裁定不写个人状态与共同障碍标志；提交用例把快照原样交给写入端口。

仍未迁移：`turn_orchestrator` 的位置意图守卫仍直接读 `turn_records` 的 `target`；
`begin_turn` 直接清理存档键；`turn_effects` 仍直接检查 `PENDING_KEY` 是否存在。
这几处只读或只清理整键，迁移收益小，暂不改动。
批次裁定编排、导航读取、角色名字匹配和展示仍在原服务。

### 再下一步的评估

剩下的主要收益在批次裁定编排：`_adjudicate_one` 同时读位置、控制权、导航与原话，
可以引入窄读取端口（位置与控制权快照、可达性查询、出口解析），让编排进入应用用例。
这一步牵涉面明显大于记录类型化，应单独一轮完成，并先为现有编排行为补齐表驱动测试；
不要与导航算法、提示词或前端同时改。如果评估后发现端口只是把现有服务函数原样转一层，
就说明收益不足，应停止。

## 第十轮：批次裁定编排与只读导航端口

`adjudicate_batch` 与 `adjudicate_one` 已进入应用层，统一编排带头人选择、行动证据、
出口解析、通行与检定需求、跟随者选择和批次占用冲突。返回的 `Decision` 只包含值及角色 ID，
不含 ORM 或展示对象。相同批次使用一份写入前的 `ActorSnapshot`，位置、控制权与原话仅投影一次。
已受阻等未移动裁定也会占用角色；后续涉及已占用角色的提案仍按原顺序跳过。

服务层保留名字匹配、快照装配和结果映射，通过 `_MovementNavigation` 提供出口解析、可达性及
不可达原因三个只读操作。既有导航算法、借道规则和阻挡说明继续复用；导航端口不负责移动角色。
没有把所有服务函数包装成接口：位置与控制权通过值快照传入，只有按裁定阶段需要查询的导航保持端口。
裁定记录构建、提交用例、重生成复用和广播仍按原入口执行，未改变事务范围或存档格式。

`test_movement_adjudication.py` 用内存导航验证拒绝行动时不查导航、各阶段短路、多人提案占用、
旧门控与共同障碍兼容、沉默真人留守等编排行为。分层测试将本应用模块纳入约束，
禁止 ORM、服务层和 AI 依赖。自然语言移动数据库测试继续覆盖完整执行及回滚路径。

仍未迁移：工具默认行动者与大地图跟随入口保持现有服务适配；提交命令和记录的装配、角色名字匹配、
导航适配器和展示仍在原服务。当前已有可独立验证的裁定与提交边界，后续应按实际修改痛点决定是否继续迁移，
不应只为压缩服务文件而增加接口层。

## 第十一轮：裁定到提交批次的装配

`prepare_movement_batch` 接收 `Decision`、角色姓名映射、回合锚点及旧待检定快照，
直接生成 `PreparedMovement`（移动命令与类型化状态更新）。服务层不再先把裁定映射回 ORM 角色，
再通过 `Verdict.record` 装配记录；`Verdict` 仅用于说明展示与日志。

装配保留原规则：只有落位裁定生成移动命令；待检定裁定写个人 pending 状态及共享标志；
其他裁定只记录结果。新的待检定条目整体替换参与者重叠的旧条目，其他旧条目保留顺序和扩展字段。
已落位或受阻裁定不额外清理旧待检定条目，避免在结构重构中改变生命周期规则。

新增端口测试验证混合裁定、角色和姓名顺序、记录字段归属、旧待执行条目的保留与替换及输入隔离。
写入端口、事务范围和提交后广播保持不变。裁定与提交间的状态装配现在可以脱离 ORM 单独验证。

## 第十二轮：检定结算批次协调（架构优化第二阶段）

`settle_pending_checks` 接收待检定快照、裁定记录快照、投出的技能、`CheckOutcome` 及写入前的位置快照，
返回 `CheckSettlement`（移动命令、`MovementStateUpdate`、每条被结算条目的投骰者）。
它复用领域 `settle_check` 与 `MoveRecord.with_states`，不复制结算规则；没有任何条目变化时返回 None，
调用方不开事务。`settle_pending_moves` 只保留数据库刷新、位置快照装配、统一提交、日志和提交后的展示。

位置快照只含队伍成员：不在快照中或已离开出发处的人没有通过资格，与原来“在队伍里且仍在出发处”的判断一致。
结算日志移到提交之后，与第六轮裁定日志的处理一致，回滚的批次不再留下貌似成功的日志。

技能匹配是纯规则，移到 `domain/checks.py`；`check_gating` 保留 `skill_matches` 兼容导出。
`services/movement.py` 因此不再导入 `check_gating`，两者的互相导入消失（`check_gating.begin_turn`
调 `movement.begin_turn` 的单向依赖仍在）。结构测试禁止移动服务重新依赖检定门控，并把新应用模块纳入纯边界约束。

`test_movement_settlement.py` 不用数据库验证：多人个人检定、个人失败后他人成功不带走失败者、
共享障碍先失败后通过及已离场者判失败、全员尝试失败、重复/无关/无投骰者结果无副作用、
不在队伍快照者无资格、同一结果结算多条条目且不同技能与无关旧记录原样保留、扩展字段与输入隔离、技能匹配规则。
原数据库测试继续覆盖事务回滚、重试与提交后广播。

仍未迁移：`pending_unissued` 仍通过函数内导入回调 `planned_effects.requested_check_settled`，
是 movement 与 planned_effects 互相导入的原因；回合开始清理仍由 `check_gating.begin_turn` 调用 `movement.begin_turn`。
这两处属于回合生命周期与状态所有权，留到第三阶段一起梳理。

## 第十三轮：补挂检定与跨模块状态读取（架构优化第三阶段）

`pending_unissued(game_session, party, issued)` 不再自己查询事件：是否已为某人挂出或掷出检定，
由调用方 `planned_effects._ensure_planned_scene` 注入（内部仍是 `requested_check_settled`）。
按人补挂与共同障碍只补第一人的规则移入应用层纯函数 `checks_to_issue`。
movement 因此不再导入 planned_effects，两者的互相导入消失。签名变化只影响这一个调用方。

`turn_effects` 与 `turn_orchestrator` 不再读取移动存档键或遍历原始记录，改用
`has_pending_moves`、`has_verdict_for`。结构测试限定 `turn_moves`/`pending_moves` 字面量及
`movement.PENDING_KEY`/`MOVES_KEY`/`turn_records` 只出现在移动模块与其状态边界。

状态所有权、事务边界与已知问题见 `docs/architecture-state-ownership.md`。
