# 移动领域边界

日期：2026-10-24。

本轮把移动的个人检定与共同障碍结算，从数据库驱动的流程中抽出。目标是让业务规则能以普通值测试，避免每次修改结算语义都需要准备 ORM 和模型替身。

## 当前职责

| 位置 | 负责什么 |
|---|---|
| `app/domain/movement.py` | 不可变移动意图、通行裁定、检定结果与结算决策；个人通行、共同障碍、重复结果与参与者资格规则 |
| `app/domain/movement_language.py` | 移动原话分类与出口词识别，不读取模组或存档 |
| `app/domain/movement_space.py` | 只读空间快照与出口目的地解析，歧义时返回候选而不擅自选择 |
| `app/domain/movement_party.py` | 依据参与者快照选择跟随者、工具默认带头人及规划器提案带头人，维护真人自主行动与独行边界 |
| `app/domain/movement_evidence.py` | 原话与规划器的行动证据门槛，决定忽略、停止裁定或继续解析出口 |
| `app/application/movement_space.py` | 将模组 JSON 字段投影为不可变快照，避免保留 ORM 或可变 JSON 引用 |
| `app/application/movement_plans.py` | AI `TurnPlan` 到领域 `MovementIntent` 的转换，兼容旧 `scene_change` |
| `app/services/movement.py` | 原有公开入口、导航候选集适配、状态加载、位置资格快照、事务写入和提交后的展示 |

调用方向：原移动服务使用输入转换器取得领域意图，使用领域函数计算结算结果，再执行位置和事件写入。领域只接收角色 ID、状态和结果，不接收 SQLAlchemy Session、ORM 对象、Provider 或事件推送对象。

`settle_check` 不修改传入状态；返回的状态和角色名单以不可变元组承载。执行顺序沿用原提案顺序。参与者是否仍在出发位置由应用服务提供快照，领域规则根据资格集合决定是否允许移动。共享障碍成功时包含先前尝试失败的参与者；个人检定只允许成功者通过。

## 兼容与事务

存档键、状态字符串、接口与重生成策略不变，无需迁移数据库或重新导入模组。模型容错仍由 AI 层负责，领域不重复实现模型输出修复。

原移动服务继续拥有事务：位置、事件、待执行记录和裁定凭据一起提交；广播和配图仍在提交之后。抽取纯规则没有改变事务范围。

## 约束与验证

`test_layering.py` 新增领域依赖禁令，包含函数内导入；领域仅允许标准库及领域模块，禁止通过相对导入越过领域目录。

`test_movement_space.py` 检查多出口歧义、方位选择、别名解析、快照隔离与原话分类。

`test_movement_domain.py` 检查个人/共享结果差异、先失败后成功、离场参与者、全员失败、重复与无关结果，以及规划器转换的兼容性。原 `test_natural_movement.py` 继续验证真实编排、工具入口和数据库事务。

## 尚未迁移

这不是完整的六边形架构迁移。原话分类、空间解析、参与者选择和行动证据门槛已迁入领域，移动服务仍承担角色名字匹配、导航适配、剩余裁定编排、ORM 和展示；没有新增通用仓储接口或 Unit of Work 框架。`services` 内原有的循环依赖也尚未全部解除。

后续应按业务收益继续分离剩余移动裁定，再明确持久化和输出端口；不应仅为缩小文件而把同一套依赖复制到更多文件。其他模块不应反向引用领域以外的实现来扩展本领域。

## 第二轮：空间解析

空间快照只包含场景 ID、称谓、描述、出口与候选 ID，所有嵌套集合均使用 tuple/frozenset。
构建后修改源模组 JSON 不会改变快照。领域解析只负责判定文字指向哪个目的地，不负责授权移动。
连通图、可通行限制与地点类型仍由现有导航/场景服务提供并校验；没有复制或放宽原有通行规则。

旧的 `movement.analyze`、`movement.scene_terms`、`movement.resolve_destination` 调用入口保留，
原话分类和目的地解析的实现各只有一份。无数据库迁移或存档字段变化。

## 第三轮：参与者选择

服务层读取角色位置、控制权和本轮表态，并解析明确的个人去向，构建不可变的 `Participant` 快照。
领域函数只返回角色 ID，服务层再映射回现有角色对象；不在领域内查询数据库。
工具默认带头人和跟随者共用一组快照，避免重复解析同一角色的去向。

沉默真人不会被点名或房主默认跟随带走；独行、留守、不同位置、已有裁定和不同目的地仍优先排除。
工具默认带头人必须直接宣告行动，仅表态跟随的人不会成为带头人；原有回退角色语义保留。
`test_movement_party.py` 直接验证这些规则，原编排测试继续验证服务边界；无模组时快照保留未知去向，不调用空间解析。

## 第四轮：规划器带头人与行动证据

规划器点名后只在点名者中选择带头人，未点名才在全队中选择；排序仍然是行动表态优先、真人其次、同级保持原顺序。
所有点名者都没有表态时仍回退到第一个点名者，由证据门槛阻止无依据移动。
这与工具默认带头人的规则不同，因此保留两个明确的领域入口，不合并为带模式开关的通用排序器。

行动证据以原话优先：大地图前往交给专用入口；原话不构成行动时停止；原话构成行动但规划器未认可时仍停止。
只有两者都认可才解析出口。领域返回明确的 `ignore`、`stop`、`resolve` 决策，服务层执行分支，不读取 ORM 来判定证据。
`test_movement_evidence.py` 验证这些优先级；`test_movement_party.py` 补充点名范围、稳定排序和回退行为。
寻路、阻挡原因展示、检定需求和事务仍由原服务编排，状态字符串和对外入口不变。

## 第五轮：通行与检定需求

`assess_passage` 接收移动意图、导航返回的可达性和旧检定门控，返回不可变的 `PassageDecision`。
适用前提是行动证据成立、目的地已明确且不同于原处；这几项前置判断仍由服务编排。
规则优先级为：路径不可达 → 通道明确受阻 → 需要检定 → 允许移动。
明确受阻时不建立待检定移动，显式技能优先于旧门控，空白显式技能回退到旧门控。

领域不读取地图，也不复制导航算法。服务仍通过 `find_scene_path` 和可通行集合处理借道限制，
通过 `travel_blocker` 获取不可达的解释；终点的限制标记仍不会被直接当作通道受阻。
路径可达且通道无阻碍后，才选择跟随者并进入原有事务。存档状态、检定消费和广播顺序不变。
领域测试覆盖规则冲突与技能回退；编排测试验证“受阻且带检定”不会错误创建待检定移动。
