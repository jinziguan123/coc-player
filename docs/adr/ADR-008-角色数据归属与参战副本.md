# ADR-008：角色数据的归属与参战副本

- 状态：已接受
- 日期：2026-07-30
- 关联：[ADR-007](ADR-007-管理端点仅限本机.md)（延伸其「素材库属于本机」的思路到角色数据）

## 背景

被反复问到的一个问题：**为什么客人必须把角色卡「导入」房主的库才能玩？我希望每个
客户端只保存自己的角色库。**

期望本身是合理的，但它与当前架构有一处硬冲突：**规则引擎与 KP 都在房主机器上跑**。
整局游戏里房主的后端要不停读写参战角色的数据——

- 检定要读 `skills` / `base_attributes`（`app/rules/coc/checks.py`）；
- `HP_CHANGE` 改血、`SAN_CHECK` 改理智、疯狂与重伤改 `status`；
- 物品交换、技能成长都落在角色记录上；

而 `SessionParticipant.character_id` 是指向**房主本地** `characters` 表的外键。
所以房主必然要持有一份可读写的数据。

要做到「房主机器上一点客人数据都没有」，只能让每个客户端各跑一套规则引擎、状态变更
走事件同步、再加冲突解决——那是重写整个联机模型，且会牵动战斗轮、检定、成长全部模块。
不做。

## 决策

1. **客人入座时在房主机器上留一份「参战副本」**，原件始终留在客人自己的库里。
   这是房主权威架构的必然结果，不视为缺陷。

2. **副本是会话资产，不是房主的藏品。** `GET /characters` 默认排除「属于别人的卡」
   （`owner_token` 非空且不等于请求者）。此前没有这层过滤，房主打开「角色」页会看到
   一堆队友的卡、还能删改它们。无主的卡（AI 队友、旧数据）仍对所有人可见，否则房主
   会突然看不到自己以前建的角色。

3. **血缘用 `characters.origin_character_id` 表达**（副本 → 客人库里的原件），
   **刻意不建外键**：原件在客人库里，那个 id 在房主库里根本不存在，它是跨库标识而非
   引用完整性约束。有值即表示「这是一份副本」。

4. **回传方向是「客人拉」，不是「房主推」。** 客人的库只有他自己能写（ADR-007），
   且房主可能先退出。拉取是**幂等全量覆盖**，所以不存在「必须在本局结束那一刻同步
   成功」的脆弱时机——掉线下次进房间补拉即可。

5. **同步时机**：进入与离开房间/游戏页各拉一次，另在角色页提供手动兜底入口。
   不做定时轮询：跑团中途的中间状态没有同步价值。

6. **冲突策略**：本局结果优先（游戏中的变化是权威的），但覆盖前把原件旧值存进
   `system_data.pre_sync_snapshot`。快照不嵌套上一次的快照，否则每同步一次体积翻倍。

## 为什么这不需要分布式状态同步

关键事实：**游戏期间只有一个写者。** 客人在玩时看的就是房主那份数据，自己库里的原件
全程不动。所以这不是「两个副本并发修改要合并」（那才需要 CRDT / OT / 冲突解决），
而是「单一权威 + 事后回传」。

业界最贴近的类比是《怪物猎人》与《博德之门3》的联机：带着自己的存档进别人的房间，
任务期间在主机侧结算，结束时把结果写回自己的存档。共同点是单一权威、结束时回传、
中断有明确策略。FPS/MOBA 那套「权威服务器 + 客户端预测」解决的是实时性，与持久化无关，
不适用。

## 后果

- 客人的角色库与模组库在**体验与归属上**是独立的：原件是他的，房主看不到也管不着。
- 但房主机器上确实存在一份数据副本，这一点必须在文档与界面上说清楚，不能让用户以为
  「什么都没留下」。界面措辞用「同步一份参战副本给房主，原件仍在你自己的库里」。
- 模组库天然各自独立：客人连着房主时读的是房主的模组，而本地建卡已不再要求模组
  （`CharacterCreate.module_id` 可空）。

## 未解决

- **本 ADR 之前建立的副本没有血缘字段**，同步会静默跳过它们；重新入座会生成带血缘的
  新副本。没有为历史数据写补齐脚本（首次落地时确认过无需保留的跑团结果）。
- 副本在房主库里会随开团次数累积，目前没有清理机制（不显示、不影响使用，但占空间）。
- 若同一张原件同时参与多个房主的团，各房主各有一份副本，回传会互相覆盖（后拉的赢）。
  当前没有并发参团的场景，暂不处理。
