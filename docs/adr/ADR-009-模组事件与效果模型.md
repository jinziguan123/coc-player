# ADR-009：模组 v3 的事件—条件—效果模型

- 状态：已实施（后端 + 前端 + 迁移脚本）
- 日期：2026-11-05
- 分支：module-flow-v3

## 背景

旧结构把剧情推进拆散在五个地方：scene.events（机制点）、triggers（flag）、kind=event 的场景、
endings.when（自然语言）、clues.trigger_condition（自然语言）。三个后果：

1. 不可判定：所有触发条件都是自由文本，每轮只能让 LLM 重新猜；
2. 不可执行：「前往某处」「置标志」「进入结局」只能写在 note 里，运行时没有执行器；
3. 不可校验：断链、悬空 flag、不可达地点静默通过，等玩家撞上才发现。

实测闇暗山：79 条事件里 12 条位于 kind=event 场景，这些事件的明细从未进入 KP 上下文；
8 个触发器标志里 7 个没有任何 states 消费；开场叙述把「内容警示」当叙事朗读。

## 决策

把「事件」提升为一等公民，并用两个最小通用类型描述它：

- Event：{id, title, at, phase, once, when:{text,expr}, npcs, effects}，独立于 locations；
- Condition：六种原子（flag / at / visited / clue_known / has_item / phase）+ all/any/not 组合，
  三值求值（True / False / None=判不了）；expr 可为 null，退回模型判断；
- Effect：15 种可执行后果（check / sanity / damage / heal / goto / set_flag / clear_flag /
  reveal_clue / grant_item / remove_item / npc_state / unlock / block / ending / narration）。
  check 是唯一可嵌套分支的类型（on_success / on_failure）。

运行时契约：后端按状态算出「可触发事件」，把事件与效果清单注入 KP 上下文；KP 用
[BEAT: 事件id] 触发，系统确定性执行效果；检定与 SAN 仍走规则内核与玩家投骰，不绕过。

## 数据结构（modules 表）

新增三列（迁移 20261105_module_flow_v3）：

- schema_version：1=旧结构，3=事件模型；
- events：顶层事件数组（kind=event 的场景在写入时提升至此，不再留在 scenes）；
- validation：解析/保存时自动算出的 errors/warnings。

## 解析器 v3

- scenes 只收 location/chapter；事件写顶层 events；
- endings.when 改为 {text, expr}；
- 新增 world_setting.start（开场地点）、opening_beats（导入事件）、content_warning（桌面提示）；
- **不再输出 triggers**：一切剧情推进都写成事件，置/清标志用 set_flag / clear_flag 效果；
  states.when 引用的标志必须由事件置上，反之亦然；
- 查漏补全（supplement）也会补遗漏事件与遗漏效果。

## 校验器

module_flow.validate_module 检查：id 唯一、事件 at 有效、条件/效果合法、效果引用完整、
exits 断链、flag 生产/消费闭环、从起点可达性、结局条件。解析入库与手动保存都会重算。

## 兼容与迁移

triggers 已并入事件：入库时 triggers_to_events 会把旧触发器转成带 set_flag / clear_flag 的
事件并清空 triggers 字段；plot_progress 的剧情钩子统一从 module.events 读取，规划器、幕后推演、
导演信号共用同一口径。

server/scripts/migrate_module_v3.py 提供一次性升级（默认 dry-run，--apply 才写库）：
事件提升、start 回填、endings.when 结构化、triggers 并入、validation 重算。

## 检定分支闭环

[BEAT] 里的事件若带 check：

- 真人控制、非暗投：把 on_success/on_failure 绑定到 pending check 的 beat 字段，挂「待玩家投骰」；
- 玩家投骰后，_settle_rolled_check（正常掷骰、幸运改判、重掷都汇到这里）按成败执行分支效果；
- 自动掷路径（NPC 暗骰 / AI 队友）：_exec_dice_check 返回本次成败，_h_beat 立即执行对应分支，
  再让 KP 据结算结果续写。

## 前端

- 时间线：新增「剧情事件」区块（条件是否可判定、效果清单），旧 triggers 区块保留为空时自动隐藏；
- 关系图：优先读 exits（方向/标签/条件/隐藏），旧 connections 自动回落，条件边渲染标签。

## 已知限制

- 旧模组不自动迁移，需跑脚本或重新解析（本分支按「删掉重导」的用法设计）；
- triggers 字段保留在 API/编辑页以兼容旧客户端，但新模组恒为空数组；
- check 分支目前只处理事件里的第一条 check，多条 check 的复合事件按顺序拆分即可。
