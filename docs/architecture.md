# CoC Player 架构评审

> 版本：v2.0（2026-08-29 重写）
> 上一版是 v1.2（2026-07-31），采用「原文不动、就地标注现状」的增量方式。三轮标注之后，
> 文档一半篇幅在重复 `DESIGN.md` 的事实，另一半的结论散在删除线与「现状（日期）」里，
> 已经读不出「今天到底该做什么」。本版**推倒重写并重新定位**。

## 这份文档是什么

- **[`DESIGN.md`](../DESIGN.md) 记事实**：架构长什么样、为什么这么设计、哪些是不能破坏的
  不变量。它是给「要改这块代码的人」看的。
- **本文件记判断**：哪里不够好、影响有多大、下一刀该切哪。它是给「要决定接下来做什么的人」
  看的，带有主观取舍，会过期。

因此本版**不再复述架构画像、模块边界、运行链路**——那些在 DESIGN.md 里有图有表，
重复一份只会产生两个可能不一致的真源。带约束力的决策见 [`docs/adr/`](adr/)。本文件只保留评审。

度量口径：源码行数不含测试与 fixture；圈复杂度用仓库内的 AST 计数（`if`/循环/`except`/
`with`/布尔子句/推导式各计一），**比常见工具偏严**，跨工具比较无意义，跨版本比较有意义。

## 一页结论

架构方向仍然成立，且这一个月经受住了一次实打实的检验：`world_state` 拆表、叙事流解析重写、
上下文装配重构三件事各自动了核心链路，**没有一件需要推翻既有设计**——这说明当初画的边界
（AI 只做语义裁定、事件日志唯一序号、进程内实时态、契约可生成）是对的。

这一轮最重要的变化不是某个模块变好了，而是**判断开始被固化成闸**。上一版评审里那些
「应当」「建议」「等需要时再做」，绝大多数到这一轮仍原封不动——因为没有任何东西阻止它们
腐烂。现在有五道纯靠测试立住的门禁（分层方向、双路径等价、两组金标准、架构图一致性），
外加行数红线。**这是本轮唯一的结构性进步，其余都是局部改善。**

仍然立着的问题只剩两类：

1. **模组导入链路是新的复杂度高地**，而且是全库风险最高的地方——`excel_import`
   圈复杂度 77、覆盖率 **9%**。
2. **`turn_orchestrator` 与 `session_service` 仍是汇聚点**，只是不再是「上帝模块」。
   它们的问题从「什么都干」变成了「知道得太多」。

## 一、上一版评审的结算

只列有变化的条目。**没有变化的也写明「未动」**——只记好消息的现状标注没有价值，
这条纪律从 v1.2 继承。

### 已解决

| 条目 | 当初的判断 | 现在 |
|---|---|---|
| `world_state` 过度承载异构状态（P1） | 「拆表一项未做，新读写口径调用点仍是个位数」 | **完成**。战斗、追逐、导航、统计、幂等台账、战报各自成表；回合级 `pending_*` 进 `turn_state`；JSON 里只剩剧情记忆，且逐键定型（`WorldStateSchema`）。顺带修掉一处静默错误：`improvised_npcs` 被误声明成 `list`，运行时全是 `dict`——因为校验 fail-open，这个错没人发现 |
| `session_service.py` 边界过宽（P1 头号问题） | 「未动，且已涨到 1,719 行，成为最大单文件」 | **部分完成**。导航（`navigation_service`）、回合态（`turn_state_service`）、事件仓库（`event_store`）已拆出，本体降到 1,207 行、不再是最大单文件。**但席位、权限、房间码仍在一起**，见下文「仍然立着的问题」 |
| 页面级大组件继续变大（P1） | 「判断维持不变，需要复核的是是否已经开始产生 bug」 | **判断不变，但加了闸**。`apps/web/tests/fileSize.test.ts` 按当前行数就地封顶、只降不升。这比继续讨论「该不该拆」有用——原来的结论「等需要写测试时再拆」在实践中等于永不拆 |
| SSE 协议版本与游标语义（P2） | 已在 v1.2 标记完成 | 维持 |

### 未动

| 条目 | 现在的证据 | 判断 |
|---|---|---|
| REST 强类型覆盖不完整（P1） | 135 条路由，40 条声明 `response_model`（30%）。会话域的历史、战斗、追逐、库存、`/sync` 仍是匿名 `dict` | **未动，且优先级应下调**。前端由 OpenAPI 生成类型，匿名 `dict` 的实际代价是「前端手写几个 DTO」，不是正确性问题。它当初排在 P1 偏高了 |
| `done` 先于后台收尾广播（P1） | `_finish_generation` 仍是「先广播 `done`，再 spawn 收尾」 | **时序未变，但成因已澄清**：收尾从主模型改到快模型（此前实测 30.9s），且现在知道了这 30.9s 不只是后台慢——**下一回合开头要等它 drain 完才能动 `world_state`，它直接变成玩家的等待**。这条的真实问题是「后台收尾会阻塞下一轮」，不是「客户端看到 done 时状态未终态」 |
| 向量存储无 `VectorStore` 抽象（P2） | 规模仍是千级块，暴力余弦 | 结论不变，不提前引入 |
| 信任边界仍是 MVP 级（P0） | 无 TLS、无账号体系，`X-Player-Token` 明文 | 按 [ADR-001](adr/ADR-001-桌面优先与可信局域网边界.md) 刻意如此。内置直连提供了机器级公钥认证，但它认证的是「哪台机器」不是「谁在玩」，不降级 |
| 实时态只在进程内（P0） | 未变 | 按 [ADR-005](adr/ADR-005-进程内实时态与扩展触发条件.md) 刻意如此 |

### 新增：上一版没看到的问题（本轮已解决）

这几条不在旧评审里，因为旧评审是按「模块大小」看的，看不见它们：

- **分层方向倒置**：`services/` 与 `ai/` 反过来 import `api/`（AI 配置的存储实现寄生在
  `api/ai_settings.py` 里）。已抽成 `ai/profile_store`，并立了闸。
- **六处假的「循环依赖」**：`ai/` 下留着 `# 局部导入避免顶层循环依赖` 的注释，而那个循环
  **根本不存在**，注释比代码旧了几个月。这是本轮最有代表性的发现——**没有闸的判断会腐烂到
  连它自己都不知道**。
- **`filter_narration_stream` 圈复杂度 109**：位于所有叙事必经的路径上，直接测它的只有一个
  文件。已拆成状态机 + 说话人两层（最高 18），并铺了金标准与分词不变性测试。
- **双路径无等价性契约**：工具路径与文本兼容路径是刻意保留的双实现，但只有各自的用例测试，
  没有任何东西保证两者行为一致。已补契约（逐步比对 + 空比对哨兵 + 清单覆盖闸）。
- **`full_response` 随分词漂移**：命令标签终止流时，尾巴残留多少取决于 Provider 怎么切词，
  而它正是下游指令解析的输入——`[SET_FLAG: a][SET_FLAG: b]` 里第二条**时而执行、时而不执行**。
  已修。这类缺陷在跑团现场几乎不可能被认出来，玩家只会觉得「flag 偶尔没生效」。

## 二、仍然立着的问题

按「对系统性演进的影响」排序，不按代码风格排序。

### 1. 模组导入链路是新的复杂度高地，且覆盖极低

叙事链路的复杂度被压下去之后，热点整体移到了导入侧：

| 函数 | 圈复杂度 | 所在文件覆盖率 |
|---|---|---|
| `excel_import.parse_coc_character_sheet` | 77 | **9%** |
| `module_service._normalize_map_nodes` | 86 | 92% |
| `module_service._merge_supplement` | 63 | 92% |
| `human_kp_actions.execute_human_kp_action` | 61 | — |
| `module_map_service.enrich_module_map` | 47 | 80% |

`module_service` 那两个虽然复杂，但有 92% 的覆盖兜着，属于「难读但有网」。
**真正的风险是 `excel_import`**：圈复杂度 77、覆盖率 9%，而它是玩家把自己角色卡导进来的
入口（COC 七版半自动人物卡，还要兼容常见变体布局）。解析错一个字段，影响的是整场跑团的
判定基线，且错得很安静——属性填错不会报错，只会让检定难度悄悄偏移。

这也是**失败形态最隐蔽的一类**：叙事出问题玩家当场就能看出来，导入出问题要等到几十轮后
某次检定「手感不对」才可能被怀疑。

**建议**：不必重构，先补测。用几份真实模板（含变体）建 fixture，把解析结果钉成金标准——
和叙事流那套同款。复杂度可以留着，覆盖率不能留在 9%。

### 2. `turn_orchestrator` 与 `session_service`：从「什么都干」变成「知道得太多」

`turn_orchestrator` 2,337 行、扇出 20 个模块，仍是最大单文件。但它的问题已经变了：
拆分之后它不再兼任实现者，风险从「改一处崩一片」变成**它是唯一同时知道
「规划器 + 队友 + 工具循环 + 分头 + 战斗 + 落库 + 广播」的地方**。

`session_service` 同理：导航、回合态、事件仓库拆出去之后，剩下的席位 / 权限 / 房间码
其实是一个内聚的簇（都围绕「谁在这个房间里、他能做什么」），继续拆的收益已经不大。

**建议**：这两处**暂缓**。真正值得做的不是继续按行数拆，而是给 `turn_orchestrator` 的
回合用例补一层端到端断言——目前它的正确性主要靠下游模块各自的单测拼出来，没有一个测试
说得清「一个完整回合应该产生哪些事件、什么顺序」。

### 3. `services/` 是两层挤在一个目录里

会 import `ai/` 的是编排服务，不 import 的是领域服务，`ai/` 夹在中间。这一点现在写进了
DESIGN §4.10 并有测试守着，但**目录本身没拆**——也就是说分层靠测试维持，不靠结构自明。

**建议**：不单独开一刀。等下次有理由大范围动这批文件时顺手做，届时收益是让新人从目录就
读得出方向，而不必先读一份文档。

### 4. 双路径的长期成本

工具路径与文本兼容路径要一直保持行为等价。现在有契约守着 `state` 类工具，但
`check` / `lookup` / `npc` 三类因带掷骰随机性或要调模型，仍只有各自的用例。
`_process_commands` 圈复杂度 58、275 行，是纯为降级存在的。

**建议**：定一个退役条件而不是无限期保留。例如「主流 Provider 的工具调用支持率达到 X」
或「连续 N 个版本没有用户回退到文本路径」，到了就删。现在的状态是**没有退役条件**，
于是它会一直在。

### 5. 观测仍以日志为主

`usage_tracker` 按 task 归集了 usage，各环节也补了耗时日志（这一轮才知道二次 planner
占一个回合 44% 就是靠它）。但仍**没有可回放的 generation trace**——出问题时能看到
「慢在哪一环」，看不到「当时喂进去的上下文长什么样」。

**建议**：优先级不高，但如果要做 AI 质量迭代，这是前置条件。`context_estimate` 已经能
零成本复现装配分项，离「把一次生成的完整输入存下来」只差一个开关。

## 三、刻意不做的事（及其触发条件）

这一节的价值在于：**把「不做」写成决定，而不是遗漏**。

| 不做 | 触发条件 |
|---|---|
| 公网暴露（TLS + 账号体系） | 产品定位改变。当前跨网走内置直连或覆盖网络，见 [ADR-001](adr/ADR-001-桌面优先与可信局域网边界.md) |
| Redis / 任务队列 / 多进程 | 见 [ADR-005](adr/ADR-005-进程内实时态与扩展触发条件.md) 的触发条件。桌面版天然单进程，现在不存在「加了 `--workers 4` 就悄悄失效」的路径 |
| 向量库 | 数据规模超出千级块，暴力余弦成为瓶颈 |
| 微服务化 | 无触发条件——领域复杂但并发极小，网络边界只会增加成本 |
| 拆分页面级大组件 | 撞到 `fileSize.test.ts` 的红线时，把新增内容放进新组件；或该组件开始产生 bug |
| 完整 DnD 规则引擎 | 目前 `rule_system` 枚举允许 `dnd`、README 明确标注未实现。**这个缺口应当收窄**——枚举允许而引擎不存在，是调用方误解的来源 |

## 四、下一刀切哪里

按「投入产出比」排，不按严重度排：

1. **给 `excel_import` 补金标准测试**（半天到一天）。风险最高、覆盖最低、做法现成
   （复用叙事流那套语料 + 快照 + regen 脚本）。
2. **给完整回合补端到端断言**（1–2 天）。这是 `turn_orchestrator` 唯一缺的那层网，
   补上之后「继续拆它」这件事就可以彻底放下。
3. **给双路径定退役条件**（半小时的决定，不是代码）。
4. **收窄 DnD 的表述面**（半天）。让 `rule_system` 的可选值与实际有引擎的规则系统对齐，
   或在建卡入口就挡住。

其余的——`response_model` 覆盖、`services/` 目录拆分、generation trace——都属于
「有理由动那批文件时顺手做」，不值得单独开一刀。

## 六、结论

上一版的结论是「在完成这些收敛之前，继续堆叠新功能会放大已有复杂度」。这句话这一轮
**部分被推翻了**：`world_state` 拆表、叙事流重写、上下文注册表都是在功能持续迭代的同时
完成的，复杂度不但没放大，几处核心热点还降了一个数量级。

原因不在于「先收敛再开发」，而在于**每一刀都先铺网再动**——金标准测试、分词不变性、
等价性契约都是在重构之前写的。这条经验比任何一条具体的架构建议都重要：

> 大型重构的风险不来自改动本身，来自**改完之后没有任何东西告诉你哪里变了**。

所以本版的核心建议不是「接下来拆哪个文件」，而是：**凡是判断，就立成闸**。
这个仓库里现在最值钱的不是那几次重构，是那五道会失败的测试——它们让「我们决定这样做」
在下一个人接手时仍然成立，而不是变成一句需要考古才能理解的注释。
