# 规则引擎组件化设计（草案）

- 状态：已评审，待实施
- 日期：2026-10-14
- 相关：ADR-001（部署边界）、ADR-004（AI 语义裁定与规则确定性变更）、`docs/coc-rule-coverage.md`

## 1. 目标

1. **房主能自定义规则，而且不用写代码**：调参数、改数据表、启用或停用官方提供的规则变体，都在界面里完成。
2. **官方规则只是一套预设**：CoC 7e 拆成若干子规则组件。项目对外发布时只附带一个官方预设，房规是叠在它上面的覆盖层。
3. **规则只有一个事实来源**：引擎结算、KP 提示词、前端展示，都从同一份"生效规则"生成，杜绝今天这种三处各写一套的漂移。

非目标：
- 定制规则需要写代码：房主的日常定制只靠界面和声明式数据完成。
- 运行时热加载代码组件，原因见第 7 节。
- 本期不做第三方代码组件的安装和分发，但接口要为它留好位置，见第 7.1 节。
- 这一轮不实现第二个规则系统。接口要为它留好位置，但遵循"三次法则"，等真有第二套系统再泛化。

## 2. 现状问题（已核实）

| 问题 | 位置 | 后果 |
|---|---|---|
| `RuleEngine` 抽象被绕过：services 直接 import `app.rules.coc.*`，涉及约 10 个文件 | `turn_orchestrator`、`combat_service`、`turn_effects`、`api/characters.py` 等 | 换规则、加变体都要改业务层 |
| 叙事扣血自己写死"半血即重伤" | `services/turn_effects.py:479` `dmg >= max_hp // 2` | 村规 `major_wound_divisor` 对叙事伤害无效，和战斗内的 `resolve_wound` 两套口径 |
| 战斗、追逐里的检定没传村规 | `rules/coc/combat.py:235-353`、`chase.py:29-49` 调 `resolve_skill_check` 时都不带 options | 大成功/大失败/奖惩骰上限的村规在战斗中失效 |
| KP 提示词写死规则书原文 | `ai/prompts/kp_system.py:124` 写"单次损失 ≥5 临时性疯狂" | 和代码默认口径"当前 SAN 的 1/5"相反，KP 说的和系统判的对不上 |
| 前端村规面板字段写死 | `VillageRulesPanel.tsx`、`lib/villageRules.ts` | 每加一条村规要改前后端两处 |
| 前端重算派生值 | `features/characters/cocDerived.ts` | 公式复制了一份，改规则时容易漏改 |
| 状态严重度表重复维护 | `turn_effects.py:72` 与 `rules/coc/status.py` | 同上 |
| 数据表写在 .py 里 | weapons / occupations / specializations / equipment / madness 症状 / 技能表 | 房主无法改 |

结论：在谈"插件化"之前，现有规则已经在漂移。组件化的第一收益不是可扩展，而是**收口**。

## 3. 设计原则（借鉴 deepseek-harness / Cordis）

| harness 的做法 | 本项目的取舍 |
|---|---|
| 内核没有特权，官方功能也是插件 | **采纳**：CoC 7e 官方规则 = 一组组件加一个预设，内核只负责组装和调度 |
| 每个插件导出配置 schema，schema 直接驱动设置表单 | **采纳**：组件用 pydantic 定义 Config，导出 JSON Schema，前端按它渲染村规面板 |
| 服务独占，重复 `provide` 直接报错；工具、提示词片段重名也报错 | **采纳**：同一槽位只能有一个提供者，配置键只能有一个所有者，冲突在启动时报错 |
| waterfall 事件：调 `next()` 往下传，可短路 | **采纳**：变体规则通过包装（wrap）扩展点实现，核心流程不动 |
| 分层 patch：bundle → profile → 用户 | **采纳但改进**：按字段合并（harness 是整份替换），数据表按 `id` 打补丁 |
| 注册即副作用，返回撤销函数，可干净卸载 | **部分采纳**：生效规则是不可变对象，按配置哈希缓存，换配置就是换对象，不需要真的去卸载什么 |
| 缺依赖时静默停在 PENDING | **不采纳**：面向非程序员，缺依赖或冲突要立即给出可读的报错 |
| 进程内任意代码插件，`!!js` 表达式，HMR | **不采纳**：房主只能提交声明式数据；代码组件随版本发布 |

## 4. 核心概念

```
RuleSystem（规则系统，如 coc7）
 ├─ Component（组件）：一块子规则，Python 代码，站方提供
 │   ├─ id / 依赖 / 冲突声明
 │   ├─ Config：pydantic 模型，即村规参数，默认值 = RAW
 │   ├─ provides：独占的服务槽位，如 check.resolve、wound.resolve
 │   ├─ wraps：对扩展点的包装（中间件），带显式 order
 │   ├─ data：声明自己用到的数据表及其 schema
 │   └─ describe(config) -> 提示词片段（只描述与 RAW 的差异）
 ├─ DataPack（数据包）：YAML/JSON，职业、武器、技能等，房主可以 patch
 └─ Preset（预设）：启用哪些组件 + 默认配置 + 默认数据包
       └─ 官方预设 coc7-official

Ruleset（生效规则）= 解析（预设 ⊕ 模组推荐 ⊕ 村规 ⊕ 本局覆盖）
  不可变、带内容哈希；引擎、提示词、前端都只读它
```

### 4.1 组件接口（示意）

```python
class Component(Protocol):
    id: ClassVar[str]                      # "coc7.check"
    requires: ClassVar[tuple[str, ...]] = ()
    conflicts: ClassVar[tuple[str, ...]] = ()
    Config: ClassVar[type[BaseModel]]      # 字段默认值 = RAW；带 title/description/ge/le 供表单渲染
    data_tables: ClassVar[dict[str, type[BaseModel]]] = {}

    def setup(self, reg: Registrar, cfg: BaseModel) -> None:
        """reg.provide("check.resolve", fn) / reg.wrap("check.after", fn, order=100)"""

    def describe(self, cfg: BaseModel) -> list[str]: ...
```

### 4.2 两类扩展点

- **服务槽位（独占）**：如 `check.resolve`、`san.check`、`wound.resolve`、`derived.compute`、`improvement.check`。一个槽位只能有一个提供者。想替换就换组件，比如用 Pulp 的理智组件替换官方理智组件，并在声明里写明 `conflicts`。
- **包装点（可叠加）**：如 `check.after`（拿到检定结果后可以改写，或附加"可花幸运"之类的提议）、`wound.after`、`san.after`。按 `order` 排序执行，可短路。

钩子调度**采用 [pluggy](https://github.com/pytest-dev/pluggy)**（已确认）。它的 `wrapper=True` 就是中间件链，`tryfirst`/`trylast` 加注册顺序可以表达优先级；它是纯 Python、零依赖，sidecar 打包没有负担。服务槽位只是一个字典，不走 pluggy。

实现要点：
- 每份 `Ruleset` 持有自己的 `PluginManager`，按内容哈希做 LRU 缓存。不同房间可以同时用不同的组件组合，互不干扰。
- 用 `HookspecMarker("coc_player")` 定义所有包装点的 hookspec。组件的包装函数通过 `HookimplMarker` 注册，注册时内核校验它确实是对应 hookspec 的实现，名字拼错就报错，不会静默不生效。
- pluggy 只负责"调度"。依赖解析、冲突检查、配置键所有权这些不归它管，由我们自己的 `Ruleset` 解析器在注册组件前完成。

## 5. CoC 7e 组件拆分

| 组件 id | 职责 | 槽位 / 包装点 | Config（来自现有 `CocRuleOptions`） | 数据表 | 依赖 |
|---|---|---|---|---|---|
| `coc7.dice` | d100、奖惩骰、骰式解析 | `dice.d100` | — | — | — |
| `coc7.character` | 属性生成、年龄修正、派生值（HP/MP/MOV/DB/体格）、起始技能 | `character.create`、`derived.compute`、`skills.base` | — | 属性掷骰式、年龄段表、DB/体格表、技能表、技能别名 | dice |
| `coc7.occupation` | 职业、专精、技能点公式 | `occupation.points` | — | 职业表、专精表 | character |
| `coc7.check` | 技能检定、达成等级、大成功/大失败 | `check.resolve`；包装点 `check.after` | `critical_max`、`fumble_rule`、`dice_pool_cap` | — | dice、character |
| `coc7.sanity` | SAN 检定、临时疯狂判定 | `san.check`；包装点 `san.after` | `insanity_rule`、`insanity_flat_threshold` | — | check |
| `coc7.madness` | 疯狂发作、症状、对检定的惩罚 | 包装 `check.after`（施加惩罚骰） | — | 症状表 | sanity |
| `coc7.wound` | 伤害结算、重伤、濒死、昏迷、即死；**叙事 HP_CHANGE 和战斗共用** | `wound.resolve` | `major_wound_divisor` | 状态表（含严重度） | check |
| `coc7.combat` | 先攻、攻击/闪避/还击、急救、擒抱、NPC 行动 | `combat.*` | — | 武器表 | check、wound |
| `coc7.positioning` | 方格、射程、视线、掩体、包抄 | `position.*` | — | — | combat |
| `coc7.chase` | 追逐轮 | `chase.*` | — | — | check |
| `coc7.growth` | 成长检定 | `improvement.check` | 组件开关 = `improvement` | — | check |
| `coc7.luck-spend`（可选，官方可选规则） | 花幸运抵差值 | 包装 `check.after` | `luck_spend_max`、`luck_spend_in_combat`、`luck_spend_blocks_improvement` | — | check |
| `coc7.luck-reroll`（可选，常见村规） | 燃运重骰 | 包装 `check.after` | `luck_reroll_cost` | — | check |
| `coc7.equipment` | 装备与资产 | — | — | 装备表 | character |

几点说明：
- 现在的布尔开关（`luck_spend`、`luck_reroll`、`improvement`）变成**组件的启用/停用**，参数只描述组件内部的细节。"开一个组件"和"调一个参数"对房主来说是两种不同的操作，界面上也分开。
- **配置键保持扁平，但每个键必须有唯一所有者**（注册时检查）。这样 `rule_system_options` 和 `game_sessions.rule_options` 里已经存下的扁平 dict **不需要数据迁移**，`from_dict` 的白名单和钳制逻辑改由各组件的 pydantic 校验承担。
- `madness` 对检定施加惩罚、`luck-*` 提出补救，都通过包装 `check.after` 实现。这正是现在 `turn_orchestrator:1724-1903` 里手工串起来的逻辑，组件化之后从编排层下沉到规则层。

## 6. 房主能定制什么

| 层级 | 房主操作 | 载体 | 校验 |
|---|---|---|---|
| 组件开关 | 启用/停用可选组件，或在互斥的变体之间二选一 | 预设之上的 `components: {enable, disable}` | 依赖/冲突解析，失败给出可读原因 |
| 参数 | 表单调参 | 组件 Config 的 JSON Schema → 自动生成表单 | pydantic：类型、区间、枚举 |
| 数据 | 增删改职业、武器、技能、症状等 | 数据包 patch：按 `id` 覆盖字段，`$delete: true` 删除，新 `id` 即新增 | 每张表一个 pydantic 行模型 |
| 软规则 | 桌面约定（现有 `table_notes`） | 自然语言注入 KP | 长度上限（现有 800 字） |

数据里的公式（比如职业技能点 `EDU×2+max(DEX,STR)×2`）需要一个**安全的表达式求值器**：只允许变量白名单、四则运算和 `max`/`min`，不允许属性访问和函数定义。不要自己写解析器，优先评估 [simpleeval](https://github.com/danthedeckie/simpleeval)，或者用 Python 的 `ast` 写一个白名单节点遍历。现有的 `occupations._calc_points` 可以先评估一下是否已经够用。

### 6.1 分层合并

沿用 `rule_options_service` 现有的优先级，前面加一层预设：

```
官方预设 coc7-official  →  模组推荐  →  村规（按规则系统，桌面长期沿用）  →  本局覆盖
```

- 参数：按字段覆盖，后者盖前者，不做叠加，保持现在"哪项生效一眼可见"的特性。
- 组件开关：后者的 enable/disable 覆盖前者。
- 数据表：按 `id` 逐行合并字段。
- 合并结果 `Ruleset` 带内容哈希，提供"导出生效规则"接口，供房主核对和排错。
- 保持现有的**读时覆盖、绝不写回**语义（见 `options.py` 头注释）。检定事件里额外记一笔 `ruleset_hash`，方便回放和审计时知道当时用的是哪份规则（符合 ADR-004 的可重放要求）。

### 6.2 局中改规则：不锁定（已确认）

跑团中途修改规则，下一次结算就生效，开局时不锁快照。为了让这种变动可见、可追溯：
- 进行中的会话检测到 `Ruleset` 哈希变化时，往事件日志写一条"规则变更"事件，内容是与上一份规则的差异（可读文字，由各组件的 `describe` 生成），全桌可见。
- KP 上下文里的规则描述本来就是每回合现读，不用额外处理。

### 6.3 房规分享：导出、导入（已确认）

房规可以导出成单个文件，发给别人导入。格式在 P2 定下来，此后只能做向后兼容的演进：

```yaml
format: coc-player/house-rules
format_version: 1
rule_system: coc7
base_preset: coc7-official@1        # 基于哪个预设、哪个版本
meta: { name: "...", author: "...", description: "..." }
components: { enable: [coc7.luck-spend], disable: [coc7.growth] }
options: { critical_max: 5, luck_spend_max: 10 }
data:                                # 按 id 打补丁，见 6 节
  weapons: [{ id: shotgun-12g, damage: "4d6/2d6/1d6" }, { id: derringer, $delete: true }]
table_notes: "..."
```

- **导入只解析数据，不执行任何东西。** 所有字段经组件 schema 校验，表达式走白名单求值器。
- **缺失的组件**（比如引用了对方本机装的第三方组件）列出来，让房主选择"忽略这些项继续导入"或取消，不能静默丢弃。
- **未知的参数键、数据表、字段一律报错**，并带上路径，比如 `data.weapons[3].damge 不是已知字段`。
- **版本升级**：`format_version` 每升一次，就写一个纯函数把旧格式迁移到新格式，导入时逐级迁移。预设版本变化只提示，不阻断。
- 导出的内容就是"预设之上的差异"，和 `diff_from_default` 的思路一致，文件小，也便于人读。

## 7. 热加载的语义

| 对象 | 生效方式 | 理由 |
|---|---|---|
| 参数、组件开关、数据包 | **即时**：下一次结算读到新的 `Ruleset`，按哈希缓存，变更后自然失效 | 这才是房主真正需要"热"的部分，而且没有安全风险 |
| 代码组件 | 启动时加载，修改后需重启 | Python 模块重载会残留状态，收益很小；而且房主不写代码 |

### 7.1 部署形态：开源发布，用户本机运行（已确认）

符合 ADR-001。规则代码只在用户自己的机器上执行，所以：

- **第三方代码组件可以开放**，性质类似游戏 mod：用户主动安装，风险由机主自担，安装时要明确提示"组件会以本应用的权限运行"。harness 的 `SAFETY.md` 也采取同样的立场，即不提供隔离。
- **安全模型的重点从防恶意转向防误操作**。数据包和表达式仍然要做白名单校验，因为房规可能被导出分享，导入一份别人的数据包不应该执行任何代码。所以"数据包里只有数据，组件里才有代码"这条界线依然要守住。
- **发现机制**：P1 先只加载内置组件。等第三方组件真的有需求，再用 Python entry points（`importlib.metadata.entry_points(group="coc_player.rules")`）或固定的本地 `plugins/` 目录接入。桌面版用 sidecar 打包，用户装不了 pip 包，所以更可能选本地目录，届时再定。
- **兼容性**：组件声明它适配的规则内核接口版本（如 `api_version = 1`），不匹配就拒绝加载，并给出可读的原因。思路来自 harness 的 peer 版本检查。

## 8. 与 AI 的衔接

- **提示词**：`kp_system.py` 里写死的规则段落（检定、SAN、战斗数值）改由各组件的 `describe` 生成。默认情况下输出 RAW 摘要，改过的项输出差异。这样从根上消除"提示词说 ≥5、代码判 1/5"这类矛盾。各组件的片段用显式 `order` 拼接，片段 id 重复就报错（借鉴 harness 的 system-prompt 注册表）。
- **指令路由**：`command_protocol` 解析出的 `HP_CHANGE`、`SAN_CHECK`、`DICE_CHECK` 等，以及 `kp_tool_loop` 的 handlers，最终都调用 `Ruleset` 的服务槽位，不再直接 import coc 模块。
- **规则书 RAG** 不变。它是参考资料，不是规则的事实来源。

## 9. 与前端的衔接

- 新增 `GET /rule-systems/{id}/manifest`，返回组件列表（id、名称、说明、是否可选、依赖/冲突）、每个组件 Config 的 JSON Schema、数据表 schema。
- `VillageRulesPanel` 改为按 schema 渲染。字段的中文标题和说明写在 pydantic `Field(title=..., description=...)` 里，只维护一份。
- 删除 `cocDerived.ts`，改为调用后端的派生值计算接口（现有 `base-skills` 接口可以扩展）。代价是建卡时多一次请求，可以用防抖缓解。
- `/rules/coc/...` 路径里写死的 `coc` 改为参数。

## 10. 迁移路线

每个阶段都可以单独合入，并且**全程保持现有测试断言不变**。约 300 个规则相关用例就是行为基线。

**P0 修漂移（不依赖组件化，建议立即做）**
1. 叙事 `HP_CHANGE` 改为调用 `combat.resolve_wound`，读村规。补测试：`major_wound_divisor=3` 时，叙事伤害也按 1/3 判重伤。
2. `combat.py` / `chase.py` 内部的 `resolve_skill_check` 一律接收并传递 options。补测试：`critical_max=5` 在攻击检定中生效。
3. `kp_system.py:124` 的疯狂口径改为由 `describe` 动态生成（至少先和代码默认值对齐）。
4. 状态严重度表只保留 `status.py` 一份。

**P1 内核与收口**
1. 引入 pluggy。实现 `Component` / `Registrar` / `Ruleset` 解析器（依赖、冲突、键所有权检查）和官方预设。
2. 把现有 coc 模块**原样包装**成第 5 节列出的组件，不改算法。
3. services 和 api 只通过 `Ruleset` 调用规则。在 ruff 里用 `flake8-tidy-imports` 的 banned-api，禁止 `app/rules/` 之外的代码 `from app.rules.coc`，由 CI 守住边界。

**P1 实施记录（2026-10-15）**
- 内核在 `server/app/rules/kernel.py`，官方组件目录在 `server/app/rules/coc/preset.py`。业务层统一通过 `rule_options_service.ruleset(db, game_session)`、`ruleset_by_id(db, session_id)` 或 `app.rules.ruleset_for(system, options)` 取得本局规则对象。
- 组件把导出分成两类：`bound` 是需要读村规的结算函数，调用时自动注入本局村规，调用方传 `options` 会直接报 TypeError；`plain` 是数据表和纯函数，原样透出。属性在每次访问时现查，所以对规则模块打的测试桩依然生效。

**P2 实施记录（2026-10-15）**

**P2 收尾：一个组件 = 一个文件（2026-10-15）**
- `app/rules/coc/components/<名字>.py` 是一个完整的子规则。文件名、槽位名、组件名三者同名，例如 `wound.py`、`rs.wound`、`coc7.wound`。文件里写三样东西：参数 `XxxConfig`（默认值即规则书原文，同时负责给 KP 和玩家的文案）、算法（普通函数）、末尾的组件声明 `COMPONENT = Component(...)`。
- `preset.py` 只是一张组件清单，`options.py` 只负责把各组件的参数合成为 `CocRuleOptions`。新增一条子规则的步骤是：新建一个组件文件，再在预设清单里加一行。
- 未传村规时，各组件按**自己参数的默认值**结算，不再反向依赖合成后的村规对象，因此不会出现循环依赖。组件可以写 `Provide(__name__, ...)` 指向自身，内核在组装时才解析这个模块路径。
- 原来附属的槽位都并入所属组件：`sheet` 并入 `character`，`status` 并入 `wound`，`weapons` 并入 `combat`，`specialization` 并入 `occupation`。
- 删除了旧的 `RuleEngine` 抽象类、`rules/registry.py` 和 `CoCRuleEngine`，现在规则只有内核这一个入口。`rules/base.py` 只保留 `CheckResult`。如果某个规则系统没有某个槽位，可以用 `Ruleset.has(slot)` 判断，例如成长结算会据此降级为空结果。

**P3 实施记录（2026-10-15）**

- **数据在结算中的走法**：Ruleset 把合并后的表附在注入给组件函数的 `options` 上（私有属性，不参与相等比较和哈希）。所以"本局规则"等于参数加数据表，业务层的调用写法不变。读表的函数从原样转交（`plain`）改为自动注入（`bound`），例如 `lookup_weapon`、`resolve_skill_value`、`get_occupation`、`make_bout`。生效规则的缓存键 = (规则系统, 参数, 补丁内容摘要)。
