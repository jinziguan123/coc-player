# 房间事件分层与消息契约 + 跨网联机（设计文档）

> 2026-07-27。来源：调研《杀戮尖塔2》开发者公开的联机架构（Stray Pixels 系列）与
> 《失落城堡2》的中继服务器形态后，对本项目实时层做的一次结构性梳理。
> 本文只做设计与排期，不含实现代码。

## 〇、为什么要动

### 参考对象的做法（事实，非推测）

《杀戮尖塔2》的联机由外包开发者实现并公开了架构文章。它把网络分成**三层**：

| 层 | 职责 | 它的实现 |
| --- | --- | --- |
| Transport | 收发字节、区分主客权限 | Steam `ISteamNetworkingSockets`（NAT 穿透 + Valve 中继兜底）；ENet 走直连 IP 用于本机多开调试 |
| Messaging | 序列化/反序列化、按类型路由 | 消息先写 type ID，头里带本地玩家 ID；消费者 `SubscribeToMessage` 订阅 |
| Gameplay | 游戏语义 | `Lobby`（大厅状态镜像）+ `Synchronizer`（**每个游戏系统一个**） |

拓扑是**星形**而非网状（原文理由：全互联要维护平方级连接数，断一条整局出问题），
client 之间靠 host 的 broadcast flag 回声转发。明确**不是**确定性 lockstep，是 host 权威。

《失落城堡2》相反，自己（或用第三方，行为高度吻合 Photon Cloud）部署了区域中继：
玩家能选服、看 ping。但逻辑仍在房主机器上跑，服务器只做匹配与转发。

**结论**：这两家的传输层是在补我们已经拥有的东西（权威服务端 + 星形拓扑）。
不值得抄的是拓扑，值得抄的是**分层**和**每系统一个同步器**。

### 我们的现状与痛点

```
Tauri 外壳 ──spawn──▶ FastAPI sidecar（127.0.0.1）── 同源托管前端
                          ├─ 上行：HTTP POST（动作）
                          └─ 下行：SSE  GET /sessions/{id}/live
```

- 传输：`server/app/services/room_hub.py` 的 `RoomHub.broadcast(room_id, chunk)`。
- 编码：`server/app/services/event_protocol.py` 的 `make_chunk()`。
- 消费：`apps/web/src/api/client.ts:102` `parseSSEStream` →
  `apps/web/src/pages/GameSessionPage.tsx:691` `handleLiveChunk`。
- 身份：`X-Player-Token`，前端 localStorage 里自造的 UUID（`server/app/api/deps.py`）。
- 客人模式：`localStorage.trpg_server_url` 指向房主的 FastAPI（`apps/web/src/api/client.ts:4`）。

四个具体问题：

1. **传输层与消息层耦合**。`broadcast()` 收的是**已经编码好的 SSE 字符串**
   （`f"data: {json}\n\n"`）。想换 WebSocket 就得改所有调用点。
2. **消息类型没有单一真源**。全仓 `make_chunk("...")` 共 **21 种** type，
   全是散落在 `sessions.py` / `chat.py` / `combat.py` 等处的字符串字面量。
   前端 `handleLiveChunk` 里 **33 个 type 分支**，新增事件时没有任何机制逼前端处理。
   项目已用 OpenAPI 生成前端类型（ADR-006 / `apps/web/src/api/generated.ts`），
   但 **SSE 事件不在 OpenAPI 里**，是契约治理的裸奔区。
3. **只有增量，没有快照**。重连走 `resyncHistory()`（`GameSessionPage.tsx:671`）
   从 `GET /events` 全量重放 event_logs。跑久的房间重放成本线性增长；
   生成中途接入靠 `RoomHub._inflight` 内存 buffer 兜底，进程重启即丢。
4. **21 种 type 语义混在一个扁平命名空间里**，但它们的持久化/去重/重放策略完全不同
   —— 这才是重连逻辑要写那么多特判的根因。

## 一、分层与消息设计

### 1.1 三分法（本设计的核心）

把现有 21 种 type 按**生命周期**而非按功能归成三类，各自有完全不同的处理规则：

| 类 | 命名空间 | 现有 type | 持久化 | 重放 | 去重 |
| --- | --- | --- | --- | --- | --- |
| **流控** | `stream.*` | `generating` `done` `ready` `typing` `presence` `housekeeping` `status` | 否 | 否 | 无意义（最后一条为准） |
| **日志** | `log.*` | `dialogue` `action` `dice` `narration_full` `system` `ooc` | event_logs | 按 seq 补 | 按 `event.id` |
| **状态** | `sync.*` | `turn_state` `character_update` `inventory_update` `lobby` `seat` `end_vote` `kp_turn_ready` `kp_roll_ready` `kp_action` `started` `event_update` `event_delete` | 否（真值在业务表） | 拉快照 | 按 `version` 单调丢弃旧的 |

三条规则：

- **流控事件不进日志、不重放**，断线重连时由 `/live` 首个 `stream.ready` 重新给出权威态
  （现在已经这么做了，只是没有归类）。
- **日志事件是唯一有 id 和 seq 的**，前端按 id 去重（现状正确，保留）。
- **状态事件不再夹带业务数据当真源**，只承担「某系统变了，版本号是 N」。
  载荷可以内嵌快照做优化，但前端必须能在只收到版本号的情况下靠拉快照恢复。
  这一条把「事件流」和「状态真值」彻底解耦。

### 1.2 后端分层

**Transport 层**（`room_hub.py`）

```
broadcast(room_id: str, event: RoomEvent) -> None      # 收对象，不收字符串
```

编码下沉到传输层：SSE 时序列化成 `data: {...}\n\n`，将来 WS 时直接发 JSON frame。
业务代码从此不碰 `data: ` 前缀。

同时补两件当前缺失的传输层职责：

- **心跳**：每 15s 发一行 SSE 注释 `: ping\n\n`。
  前端 `parseSSEStream` 只认 `data: ` 开头的行，注释行天然被忽略，**不需要改前端**。
  这是走隧道/NAT 环境的必需品（见第二章），也是最便宜的稳健性改进。
- **背压**：`asyncio.Queue` 现在无界，慢客户端会把内存吃穿。设上限 + 溢出时
  给该连接推一条 `stream.desync`，让前端主动全量重连。

**Messaging 层**（新 `server/app/services/room_events.py`）

一个 Pydantic **可判别联合**作为唯一真源：

```python
class TurnStateEvent(BaseModel):
    type: Literal["sync.turn_state"]
    version: int
    payload: TurnStatePayload

RoomEvent = Annotated[Union[...], Field(discriminator="type")]
```

**让它进 OpenAPI**：加一个只为契约存在的端点
`GET /sessions/{id}/live/_schema`，`response_model=RoomEvent`。
这样现有的 OpenAPI → `generated.ts` 流水线（ADR-006）会自动产出前端的判别联合类型，
**零新增工具链**。这是本方案里性价比最高的一步。

`event_protocol.make_chunk()` 保留为内部编码函数，但业务侧不再直接调用。

**Gameplay 层**：每系统一个 Synchronizer

```python
class SystemSync(Protocol):
    namespace: str                                  # combat / hex / inventory / turn / lobby
    def snapshot(self, db, session_id) -> dict: ...
    def version(self, db, session_id) -> int: ...
```

已有系统直接对号入座：`combat_service` / `hex_map` / `inventory_service` /
`team_turn_service` / `session_service`（lobby）。

新增 **`GET /sessions/{id}/sync?systems=combat,hex&since_seq=N`**，返回各系统快照 +
当前 seq。重连流程改成：

```
开 /live（先缓冲收到的事件） → 拉 /sync 拿快照+seq → 丢弃 seq ≤ 快照的缓冲事件 → 应用剩余
```

`GET /events` 仍然保留，但只负责**日志类**的历史分页（聊天记录往上翻），
不再承担状态恢复职责。

### 1.3 前端分层

- **`lib/roomEventBus.ts`**：`subscribe(type, handler)`，替代 `handleLiveChunk` 的
  33 个分支。用生成的判别联合做 exhaustive check —— 后端加新 type 而前端没处理时
  `tsc --noEmit` 直接报错。这条是把「契约治理」落地成 CI 门禁的关键。
- **按系统拆 store**：`combatStore` / `hexStore` / `turnStore` 各自订阅自己命名空间的
  `sync.*` 事件，各自持有 version。`GameSessionPage.tsx`（2247 行）随之瘦身
  —— 这不是顺带的重构，而是分层的必然结果。
- **`sync.*` 的统一处理**：收到 version > 本地 → 用内嵌快照或回源 `/sync`；
  version ≤ 本地 → 直接丢弃。乱序和重复天然免疫。

### 1.4 排期

| 阶段 | 内容 | 风险 |
| --- | --- | --- |
| **P-Msg-1** | 心跳 + 队列背压 + `broadcast` 改收对象 | 低，纯内部重构，行为不变 |
| **P-Msg-2** | `room_events.py` 判别联合 + `_schema` 端点 + 前端 `roomEventBus` + exhaustive check | 中，要一次性梳理 21 种 type 并改名到三命名空间；**必须前后端同版本发布** |
| **P-Msg-3** | `SystemSync` + `/sync` 端点 + 重连改快照对齐 + 拆 store | 中高，动重连路径，需补重连单测 |

P-Msg-1 可以独立先上，跨网联机也依赖它的心跳。

**兼容性**：type 改名会破坏旧客户端。因为是桌面应用且房主/客人版本必须一致，
建议在 `/api/health` 里加 `protocol_version`，客人连接时不匹配就明确提示升级，
而不是让它以奇怪的方式半坏。

## 二、跨公网联机

### 2.1 现状比"局域网联机"还紧一点

`server/run_desktop.py:36` 是 `uvicorn.run(app, host="127.0.0.1", ...)`。
**打包后的桌面版实际上只监听回环，连局域网都进不来**。现在的局域网联机能力来自
开发态起服务时手动绑 `0.0.0.0`。这是要做的第一件事，跟公网无关。

同时 `docs/adr/ADR-001-桌面优先与可信局域网边界.md` 明确写了：
当前版本不承诺公网安全，不提供账号、TLS 终止、抗滥用；
「若未来面向非可信网络，必须新增独立的身份、授权、传输安全和审计设计，
不能只把当前 token 换个名字。」**任何跨网方案都要正面回答这一条。**

### 2.2 三条路，推荐第一条

按 CLAUDE.md 的约定，先看成熟开源方案，不自建。

**方案 A：覆盖网络（Tailscale / ZeroTier）—— 推荐**

房主与玩家加入同一个 tailnet，玩家把 `trpg_server_url` 填成房主的
Tailscale IP（`100.x.x.x`）。

- **代码改动几乎为零**：只需让监听地址可配置。
- **它不违反 ADR-001，而是延伸了 ADR-001。** tailnet 本身就是一个「可信网络」：
  WireGuard 端到端加密、成员身份由 Tailscale 的 SSO 负责、非成员根本路由不到。
  我们是把可信局域网从物理二层扩展到广域，而不是把服务暴露到公网。
  这是本方案最重要的论点。
- 自带 NAT 穿透，打不通时走 DERP 中继兜底 —— 正是《杀戮尖塔2》蹭 Valve 中继的同一思路，
  只是我们蹭 Tailscale。
- 代价：每个玩家要装客户端、要被邀请进 tailnet。朋友局可接受；陌生人开团不可接受。
- 不要做的事：把 Tailscale 嵌进应用（`tsnet` 是 Go 库，我们后端是 Python，
  塞进 Tauri 的 Rust 侧属于第二期以后的事）。

**方案 B：隧道（Cloudflare Tunnel / frp / ngrok）—— 需要先补安全基线**

房主起隧道拿到一个 https URL，玩家什么都不装，填 URL 即可，甚至能用手机浏览器。

体验最好，但**这就是真·公网暴露**，直接踩 ADR-001 第 3 条。当前状态下拿到 URL 的任何人：

- 可读全房间内容（`X-Player-Token` 是客户端自造 UUID，服务端不校验来源）；
- 可调用 AI 端点烧房主的 API key（无速率限制）；
- 可访问模组导入 / AI 设置 / rulebooks 等管理端点（现在没有按房主收敛）。

要走这条，前置工作是实打实的，不是加个开关：

1. token 由**服务端签发**并绑定 session（一次性邀请码换 token），不再客户端自造；
2. AI 相关端点限流 + 房间级配额；
3. 管理类端点对非房主 token 一律 403；
4. TLS 由隧道终止（Cloudflare/frp 都自带）；
5. 新写 **ADR-007** 修订 ADR-001，把「非可信网络模式」作为显式的、默认关闭的能力。

另有一个实操坑：**SSE 经反代会被缓冲/超时**。代码里已有 `X-Accel-Buffering: no`，
但 Cloudflare 对空闲长连接有超时。所以 P-Msg-1 的心跳是这条路的硬前置。

**方案 C：自建信令 + 区域中继（学失落城堡2）—— 明确排除**

我们没有运维、没有账号体系，AI 调用还在房主本地（中继解决不了成本归属）。
投入产出比最差，不做。

### 2.3 排期

| 阶段 | 内容 |
| --- | --- |
| **P-Net-1** | 监听地址可配置（默认仍 127.0.0.1），UI 里给房主一个「允许局域网加入」开关 + 显式风险提示 + 显示本机 IP/房间码 |
| **P-Net-2** | 文档化 Tailscale 方案（一页图文教程放 `docs/`），README 补「跨网联机」小节 |
| **P-Net-3** | 安全基线（服务端签发 token / 限流 / 管理端点收敛）+ ADR-007 + 可选隧道模式 |

P-Net-1、P-Net-2 可以立刻做，成本很低。P-Net-3 是独立的一期工作，
**在它完成前，不要在产品里提供任何一键公网暴露的入口**。

## 三、两块工作的关系

不是并列的两件事：**P-Msg-1 的心跳与背压是 P-Net 任何一条路的前置**
（跨网必然遇到 NAT 表项回收和慢客户端），
**P-Msg-3 的快照对齐是跨网体验的决定因素**（广域网重连频率远高于局域网，
每次都全量重放 event_logs 不可接受）。

建议顺序：`P-Msg-1 → P-Net-1 → P-Net-2 → P-Msg-2 → P-Msg-3 →（视需要）P-Net-3`。
