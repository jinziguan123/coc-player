# 内置直连组网（P-Net-4，设计文档）

> 2026-07-29。缘起：现有跨网联机方案（[`docs/跨网联机-tailscale.md`](../跨网联机-tailscale.md)）
> 要求每位玩家自行安装 Tailscale、注册账号、接受设备共享邀请。房主拍板：
> **要让朋友只装 TRPG Player 一个东西就能进团。**
> 本文只做设计与排期，不含实现代码。

---

## 〇、动机与边界

### 要解决的

玩家侧的安装与注册成本。现状是「装 TRPG Player + 装 Tailscale + 注册 Tailscale 账号 +
点开邀请链接接受共享 + 回到应用填 `100.x.y.z:8756`」，五步里有四步与游戏无关。
目标形态是「装 TRPG Player + 粘贴一串邀请码」。

### 明确**不**追求的

**「不依赖第三方服务」不是本期目标，也不可能是。** NAT 穿透在物理上必须有一个双方都能
到达的公网协调点：Tailscale 叫 DERP，ZeroTier 叫 root server，iroh 叫 relay。内置组网只是
把这个依赖从「用户显式安装的 Tailscale」换成「应用内静默使用的 relay」——依赖没有消失，
只是变得不可见。谁要是以为内置之后应用就自给自足了，那是误解。

本期起步用 iroh 官方公共 relay（免费、零运维），自建 relay 留作可切换的配置项，不在 P-Net-4 范围。

### 也不做的

- **不做虚拟网卡 / 子网代理 / 通用组网。** 我们不是在做 ZeroTier 替代品，只需要
  「客人的 HTTP + SSE 打到房主的 FastAPI」这一条通路。装 TUN 设备要管理员权限，
  跨三平台的安装体验会比装 Tailscale 更糟，与动机背道而驰。
- **不取代现有的局域网直连与 Tailscale 路径。** 三条通路并存：同一 Wi-Fi 用局域网最简单，
  内置直连覆盖跨网，Tailscale 留给已经在用它的人和内置直连打不通的兜底。

## 一、选型

选 [iroh](https://github.com/n0-computer/iroh)（Rust，1.0 于 2026-06 发布）。

| 候选 | 结论 |
| --- | --- |
| **iroh** | **选它。** 定位就是「给应用开发者的 P2P 连接层」而非「给网管的组网工具」；纯 crate，直接嵌进已有的 `src-tauri`，不需要额外进程或驱动；给对端公钥即可拨号，QUIC 打洞直连成功率约 90%，失败自动降级到无状态 relay；官方公共 relay 免费。 |
| EasyTier | 去中心化、握手节点在国内、对称 NAT 穿透率更高，这些都是真优点。但它是「虚拟网卡 + 组网」形态，落到我们身上等于自带一个 ZeroTier，与「不做通用组网」的边界冲突。**列为 relay 质量不可接受时的备选。** |
| libp2p | DHT 发现更去中心化，代价是连接成功率明显低于 iroh 的「小幅中心化换近乎确定的连通」。我们要的是朋友一次就连上，不是网络纯洁性。 |
| WebRTC / Pion | 需要信令服务器 + 有状态 TURN，栈更重（ICE/STUN/TURN/DTLS/SCTP）。只有在客人用浏览器而非桌面应用时才有优势——而我们的客人本来就装 app。 |
| Tailscale `tsnet` | 能把 tailnet 节点嵌进进程，但用户仍需 Tailscale 账号与 authkey，**不解决本期的核心痛点**；且是 Go 库，要么再起一个 sidecar，要么放弃嵌入。 |

选 iroh 的附带代价见第七节。

## 二、架构：一条 HTTP-over-QUIC 隧道

```
房主机器                                          客人机器
┌────────────────────────────┐                   ┌────────────────────────────┐
│ Tauri 外壳                 │                   │ Tauri 外壳                 │
│  └ netlink（iroh Endpoint）│◀═══ QUIC 直连 ═══▶│  └ netlink（iroh Endpoint）│
│        │ 反代               │   打不通则走 relay │        ▲ 本地监听           │
│        ▼                    │                   │        │                    │
│ FastAPI 127.0.0.1:8756      │                   │  前端 → 127.0.0.1:<本地端口>│
└────────────────────────────┘                   └────────────────────────────┘
```

- 房主侧：`Endpoint` 以 ALPN `trpg/1` 监听，每条入站 QUIC 双向流反代到本机 FastAPI。
- 客人侧：本地 `TcpListener` 每接一个 TCP 连接就开一条 QUIC 流拨向房主公钥。
  前端仍然只会连一个 `http://127.0.0.1:<port>`，SSE 长连接天然跟着走。

**后端的业务代码一行不改**，前端只改「连哪个地址」和 token 归属键（第五节）。

### 一个关键副作用：不再需要重启

隧道打到的是 `127.0.0.1:8756`，而后端**无论如何都在监听回环**。所以启用内置直连
**不需要重启应用**，也不需要打开「允许局域网加入」——甚至可以在后端只绑回环的情况下开团，
局域网上没有任何暴露面。这比现状（改开关必须重启，见 [`run_desktop.py`](../../server/run_desktop.py)）
体验好得多。

但这正说明：**隧道绕过了 ADR-001 赖以成立的「监听地址」主闸。** 因此隧道自身的开关必须
成为等效的主闸——关闭时不创建 Endpoint、不注册到 relay，做不到「热开热关」就不算数。
这一点需要新增 **ADR-008** 记录，不能默默改掉 ADR-001 的前提。

### 为什么是 HTTP 反代而不是纯 TCP 转发

纯 TCP 转发更简单，但会让所有客人在后端看起来都是 `127.0.0.1`——那是下一节要处理的安全事故。
我们需要在转发时注入来源标记，所以房主侧必须解析到 HTTP 请求头这一层（用 `hyper` 做，
响应体保持流式，不缓冲，否则 SSE 会被卡死）。

曾考虑用不同回环地址（`127.0.0.2`）区分来源，可以做到零 HTTP 解析且无法伪造——
但 macOS 需要先给 `lo0` 加 alias、Windows 行为不一致，跨平台不可靠，放弃。

## 三、来源语义改造（安全红线，必须先于隧道落地）

这是本期唯一会动后端的地方，也是唯一一处做错就出安全事故的地方。

当前代码把「来源是回环」直接当作「这是房主本人」。共四处消费点：

| 位置 | 当前行为 | 隧道接入后的后果 |
| --- | --- | --- |
| [`deps.py`](../../server/app/api/deps.py) `require_local_client` | 回环放行管理端点 | **客人可读房主明文 API key、删房主素材库、烧房主额度——ADR-007 全部失效** |
| [`rate_limit.py`](../../server/app/services/rate_limit.py) `exempt_local` | 回环豁免限速 | **客人不受任何限速，房间码枚举防护归零** |
| [`net.py`](../../server/app/api/net.py) `set_lan` | 回环可改联机开关 | 已经连进来的客人能自己放宽准入 |
| [`main.py`](../../server/app/main.py) `is_trusted_peer` | 回环永远放行 | 符合预期（隧道开关是它自己的闸），无需改动 |

### 改法

在 [`net_access.py`](../../server/app/services/net_access.py) 里把「来源」从二值升级为三态，
并保持它作为唯一真源的地位：

```
peer_kind(host, headers) -> "local" | "lan" | "netlink"
netlink_peer_id(headers) -> str | None      # 限速按对端公钥分桶
```

签名收 host 与 headers 而不是 `Request`，是为了不让 services 层反向依赖 FastAPI，
与该模块既有风格一致。

- `local`：真·房主本机。回环 **且** 不带隧道标记。
- `netlink`：经内置隧道进来的客人。回环 **且** 携带有效隧道标记。
- `lan`：其余（局域网 / 覆盖网络），沿用现有判定。

三处消费点全部改为基于 `peer_kind`：`require_local_client` 与 `exempt_local` 只认 `local`；
限速的计数键在 `netlink` 时用**对端公钥**而不是 IP（否则所有隧道客人共用一个桶，
一个人被限全体遭殃）。

### 隧道标记怎么防伪造

房主侧反代时改写 HTTP 请求头：

1. **先无条件剥离**客户端自带的任何 `X-Netlink-*` 头（防客人自己伪造）；
2. 注入 `X-Netlink-Secret: <本次启动的随机密钥>` 与 `X-Netlink-Peer: <对端公钥>`。

密钥由 Tauri 外壳在 spawn sidecar 时经**环境变量**传给 FastAPI，两端各持一份，不落盘。
后端只认与自己环境变量一致的值。于是：

- 局域网上的人直连 8756 并伪造头 → 不知道密钥，被识破，按 `lan` 处理；
- 本机其他进程能读到环境变量 → 本机攻击者已在威胁模型之外，与现有假设一致。

**没有这一节，P-Net-4 就是一个把房主 API key 送给所有客人的功能。** 它必须先做、
并且带回归测试（伪造头的请求必须不能通过 `require_local_client`）。

## 四、准入：公钥白名单，不是房间码

iroh 的 EndpointId 就是公钥，这给了我们一个比现有 `X-Player-Token` 结实得多的准入原语——
token 是客户端自造的明文串，公钥不可伪造。

- 房主生成**邀请码** = 房主 EndpointId + 房间码，编码成一串可复制的文本（base32，
  分组显示便于口述）。
- 房主侧持久化**已授权公钥白名单**。陌生公钥拨号时不直接反代，而是挂起并在房主界面弹出
  「有人请求加入」，房主批准后才放行并入白名单；拒绝则断开。
- 白名单可在「设置 → 联机」里查看与吊销。

这等于把 ADR-001 的「可信」从网络层（相信同一个局域网里的人）搬到密码学层
（相信房主亲手批准过的那几个公钥）。**但它不解决 ADR-007 遗留的问题**：
公钥认证的是「哪台机器连进来」，`X-Player-Token` 仍然是席位归属的明文串，
素材库的读仍对客人开放。P-Net-3 的「服务端签发 token」仍然欠着。

## 五、客人侧的地址稳定性（一个容易漏掉的回归）

前端 [`client.ts`](../../apps/web/src/api/client.ts) 的 `getPlayerToken` **按 serverUrl 隔离 token**
（ADR-007 的改动）。隧道客人的 serverUrl 是 `http://127.0.0.1:<本地端口>`——
如果端口每次启动都变，`trpg_player_token::http://127.0.0.1:54321` 这个键就跟着变，
**客人每次重连都会丢席位**。

改法：把 token 的归属键从「URL」抽成「主机身份」：

- 隧道连接 → 用房主公钥；
- 局域网连接 → 沿用 URL（保持现状）。

顺带修掉一个既有隐患：房主机器换了局域网 IP 后，现在的客人同样会丢席位。

客人侧另外应持久化「房主公钥 → 本地端口」映射并尽量复用同一端口，端口被占时再另分配。
这只为减少界面上地址变来变去的困惑，不作为 token 稳定性的依赖。

顺序不可调换：**4a 必须先于 4b**，否则中间状态就是可利用的漏洞。

### 4b 已验证到什么程度（重要，别高估）

自动化测试用内存管道代替 QUIC 流，跑通了**反代这一层**：标记注入、伪造头被覆盖、
keep-alive 复用连接时每个请求都带标记、`X-Player-Token` 不被误伤、后端不可达时回 502、
SSE 分块在后端仍持有连接时就已抵达客人侧（即没有被缓冲）。

**iroh 那一层完全没有自动化覆盖**：连接建立、discovery、打洞、relay 降级、字节泵，
都只能靠两台真机跨网验证。也就是说，当前代码「逻辑上是对的」，但**从没有真的连通过一次**。
真机验证清单见第七节。

### 4c 撞上的架构约束：前端默认调不到 Tauri 命令

设计时没料到的一点：应用启动后窗口从 loader 跳到 `http://127.0.0.1:<后端端口>`，
**那之后属于 remote origin，默认拿不到 Tauri IPC**（Tauri 只把 API 给随包分发的代码）。
这正是 `apps/web` 此前一行 Tauri 调用都没有的原因——它根本调不了。而隧道跑在 Rust
进程里，后端（Python）不知道它存在，所以设置页必须能跟 Rust 说上话。

两条路：

1. **给 capability 加 `remote.urls`**，放行 `http://127.0.0.1:*`；
2. **让 Python 后端转发**：Rust 另开一个只绑回环的控制端口，后端代理过去，
   前端仍然只跟后端说话，管理端点天然继承 ADR-007 的「仅限本机」。

初看 2 更安全，实际不然：**前端页面本身就是回环来源**，一旦前端被注入，攻击者
已经能直接调用房主专属的全部 HTTP API（读 AI 配置、删素材库）。两种方案在 XSS 下
都已失守，2 的安全优势只是「不额外暴露 IPC 通道」，却要付出数倍复杂度。

因此选 1，但收窄到最小面：新增独立的 `src-tauri/capabilities/netlink.json`，
`permissions` 留空（不追加任何 core 权限），只让页面能调应用自身的 `netlink_*` 命令。
遗留风险记在这里：Tauri 文档明确指出 **Linux/Android 上无法区分 `<iframe>` 与主窗口**，
若将来前端引入可被注入的 iframe，这条 capability 会成为一条额外的利用路径。

### 引入 iroh 的工具链代价

iroh 1.0 要求 Rust ≥ 1.91，因此 `src-tauri/Cargo.toml` 的 `rust-version` 从 1.77.2 提到 1.91。
CI 当前不构建 Tauri 侧（只跑后端、前端、gitleaks），所以不受影响；但本地开发需要
`rustup update`。另外 `tauri.conf.json` 的 `bundle.resources` 从 `resources/trpg-server/**/*`
放宽到 `resources/**/*`，并加了一个纳入版本库的 `src-tauri/resources/README.md`——
Tauri 的 glob 匹配不到文件会直接报错，而 `trpg-server/` 由打包流程生成、不进库，
于是开发态连 `cargo test` 都跑不起来，Rust 侧测试等于没人跑得动。

## 七、风险与代价（提前认账）

- **relay 在境外。** iroh 公共 relay 节点不在国内，打洞失败的那约 10% 会走跨境中继，
  延迟与稳定性都会明显退化。缓解手段是自建 relay（又要一台公网服务器）或切 EasyTier。
  UI 必须显示「直连 / 中继」状态，否则房主只会觉得「这软件时好时坏」。
- **打包体积。** iroh 及其依赖会让二进制涨若干 MB，需实测。
- **UDP 被全封的网络**（部分企业网、校园网）只能走 relay，体验退化。
- **async runtime 集成**：Tauri 已有 tokio runtime，iroh 需挂在同一个上，别起第二个。
- **三平台实测不可省**。NAT 行为、防火墙提示（Windows 首次会弹）、休眠唤醒后的重连，
  都只能在真机上验。

### 真机验证清单（4b 的实际完成门槛）

两台不同网络的机器，房主侧调 `netlink_start` 拿到 EndpointId，客人侧
`netlink_connect` 后把前端指向返回的本地端口：

1. 能连上，房间列表能拉到；
2. 开团后 SSE 持续推送，不断流、不卡顿；
3. 客人的「设置 → AI 配置」拿到 403（隧道标记生效，ADR-007 没被绕过）；
4. 客人反复请求房间码会被限速（按公钥分桶生效）；
5. 断网重连、房主休眠唤醒后的行为；
6. Windows 首次运行的防火墙弹窗是否阻断 UDP。

第 3、4 条是安全项，跑不通就不能发布。

4c 追加：

7. 设置页能调到 `netlink_*`（即 capability 的 `remote.urls` 真的生效）——
   这条是 4c 全部 UI 的前提，**在浏览器里测不出来**；
8. 陌生人连入时房主界面弹出待批准项，同意后对方无需重连即可进入；
9. 客人退出重进后**席位还在**（token 按 `netlink:<公钥>` 归属而非按本地端口）；
10. 吊销后对方断线重连会被挡住（注意：不会踢掉当前已建立的连接）。

## 八、不在本期解决

- `X-Player-Token` 仍不是身份认证（ADR-007 遗留）；
- 素材库的读仍对客人开放；
- 房主与客人之间是 QUIC + TLS 1.3 加密的，但**局域网直连路径仍无 TLS**，未变化；
- 自建 relay、relay 选区、连接质量调度。
