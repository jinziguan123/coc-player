# 架构后续验收与优化提示词

以下五段按顺序执行。每段开始先检查 Git 状态和前一段结果，避免重复修改。

## 共同约束（每段均适用）

在 coc-player 仓库工作。所有回复和提交说明用中文。先读项目约定，优先使用可用的代码图工具；没有工具时用 AST 和源码。保留无关未跟踪文件。不要推送远端，不要调用付费或真实 LLM 服务。完成有意义的一组修改后运行后端全量 pytest、Ruff 和 git diff --check，成功后提交。保持存档兼容，除非有明确证据，不引入通用仓储、DI 框架或大范围目录搬迁。区分已证实问题、风险和未验证行为。

## 1. 重审间接依赖环

对 server/app 建立可复跑的静态导入图，包含局部导入、包内相对导入，明确 __init__、动态导入和兼容导出的处理限制。计算全部强连通分量，列出实际循环路径及对应源码位置。不能用“没有直接双向导入”代替“没有间接环”。核实关键路径的业务职责，按实际风险给出处理顺序，更新审计证据。不要只为降低模块数拆文件。

## 2. 核心移动链路验收

从玩家意图到持久化及 KP 上下文检查：独自穿过拱门、队友留守、障碍需要检定、检定成功/失败、分队重聚、同回合重生成、落库失败后重试。先清点已有测试，补缺失的跨层断言，不复制纯实现测试。测试应检查实际位置、队友位置、移动事件和上下文看到的状态；不能只断言模型输出文本。用确定性模型替身，不调用真实 LLM；明确真实模型理解和叙述质量尚未验证。修复发现的确证缺陷并验证。

## 3. 审查跨模块事务和重试

重点检查自动检定记录与物品/线索兑现、人工 KP 挪人后的目的地公开与行动事件。逐一追踪内部 commit，定义什么必须一起成功、什么允许提交后执行。用真实数据库失败注入证明现有问题，再修复；验证失败不会丢失待兑现收益，重试不重复发物品，移动与公开信息及事件一致。禁止用外层 transaction 包住仍然内部提交的函数假装原子性。配图和广播不跨网络持有数据库事务。明确未解决的进程崩溃/请求重放语义。

## 4. 按职责收拢编排

基于前三步证据，从 turn_orchestrator、kp_tool_loop、planned_effects、turn_effects 中选择最值得提取的一项明确职责。分离业务判断、持久化与外部副作用，保持原入口兼容。可直接利用第三步发现的收益结算职责，避免额外制造抽象。增加依赖边界约束，并以现有业务测试证明真实接线。若没有值得拆的部分，给出证据并明确暂缓，不机械拆文件。

## 5. 整理当前架构文档

将 docs/architecture-state-ownership.md 整理为单一当前状态，消除正文与追加更新冲突。审计报告区分历史基线与最新扫描结果。写清状态所有者、事务边界、兼容入口、已验证范围、尚存依赖环及真实模型验收限制。核对文档中的函数、调用方向和测试数量，不能继续把历史“28 模块”或“尚未实施”描述当成当前结论。保留必要历史链接。
