# 后端架构审计（当前结论）

更新日期：2026-10-25。目标是减少实际职责耦合、明确状态与事务所有权，保持存档和业务语义兼容。

## 当前结论

项目是逐步分离职责的现有分层架构，移动领域已有独立规则、应用用例和持久化适配边界；
尚不能称为整个项目都符合六边形架构或完整 DDD。收益结算和队员查询已独立，服务目录仍混合多种职责。

## 可复跑的依赖证据

执行 `python3 scripts/audit_import_graph.py`，当前快照见 [静态图结果](architecture-import-graph.json)。
最新结果：225 个模块、972 条显式依赖边，一个 **22 模块强连通分量**。
本次后续工作的同口径起点为 224 个模块、961 条边、26 模块分量；提取收益结算后缩至 22。
边数增加来自显式新模块依赖，不能将边数或文件数直接当作架构质量指标。

扫描包含 `__init__.py`、函数内导入、相对导入和静态条件分支内的导入。
`from package import submodule` 优先归属真实子模块；导入符号则归属声明它的模块。
不执行代码，不展开动态导入、兼容导出符号真实归属及父包隐式初始化。
这是一份静态依赖证据，不证明所有边都会在同一运行路径执行，也不代表必然发生循环初始化错误。

仍存在的已核实循环：

`ai.context → combat_service → npc_state → ai.context`

NpcState.load 为解析当前 NPC 的剧情标志状态，调用 AI 上下文的私有解析函数；
上下文又依赖战斗服务。共享状态解析的归属仍可改善。完整分量成员、循环边和行号见 JSON。
历史“28 模块”和“无直接双向边”的结论不替代本次间接依赖审计。

## 后续候选与限制

1. NPC 状态解析仍反向依赖 AI 上下文；适合单独提取共享纯规则，随后重扫依赖图。
2. turn_orchestrator、kp_tool_loop、turn_effects 等仍包含较多编排职责；按新需求或确证问题拆分，不按行数拆文件。
3. 骰子、移动、收益并非整个回合同事务；进程崩溃后的自动续跑与配图可靠补发未实现。
4. 人工 KP 成功请求的重复投递尚无请求级幂等键，本次只验证失败回滚后的安全重试。
5. 使用确定性模型替身验证了位置、事件及 KP 输入上下文；真实模型叙述质量尚未实测。

未引入通用仓储、DI 框架或前端改造。数据库与模组格式不变，无需重新导入模组。
