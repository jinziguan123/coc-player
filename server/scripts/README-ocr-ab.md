# 图文模组解析 A/B：直接喂图 vs OCR 前置

实验分支 `feat/qwen-ocr-module-parse`。目的是量出「先 OCR 再走文本链路」对**图文/扫描件模组**
的解析质量提升有多大，值不值得转正。

## 先填 key（不写进代码，走设置页）

本项目的约定是「AI 密钥的唯一真源是设置页」（见 `app/config.py` 的注释），所以 DashScope 的 key
不放 `.env`、也不放代码里。填法：

1. 打开 **设置 → AI 配置 → 新建配置**
2. 三个字段：
   - `base_url`：`https://dashscope.aliyuncs.com/compatible-mode/v1`
   - `model_name`：`qwen3.7-plus`（Qwen-MM-Plugins 里 OCR 用的默认模型；`qwen-vl-max` 等同样可用）
   - `api_key`：你的 DashScope key
3. 保存后点该配置的 **「设为视觉模型」**

带团用的主模型不用动——OCR 只走视觉槽位。想换成本机部署的视觉模型，改这一个配置即可。

## 跑对比

```bash
cd server && .venv/bin/python scripts/ab_ocr_parse.py /path/to/某本图文模组.pdf
```

也可以直接喂多张扫描页图片。脚本**不写库**，两条链路的产物落在 `output/ab_ocr/`：

- `A_直接喂图.json` — 现状：图片一次性喂给视觉模型直接出 JSON
- `B_OCR后走文本链路.json` — 实验：逐页 OCR → 拼成原文 → 走文本解析
- `B_ocr原文.txt` — OCR 出来的原文，用来判断是「认字不准」还是「理解不到位」

终端会打一张对比表：场景数、场景机制点、NPC 数、带属性的 NPC、线索、手书、结局、
幕后真相字数、手书正文字数、各自耗时。

## 也可以走上传接口

```bash
curl -F "files=@某本图文模组.pdf" "http://127.0.0.1:8000/api/modules/upload?rule_system=coc&ocr_prepass=true"
```

`ocr_prepass` 默认关，行为与主干完全一致；打开才走 OCR 前置。

## 为什么预期会有提升

图片链路是**一次性调用**：最多几张图 + 一句提示词直接产出结构化 JSON。文本链路有两样它没有的
东西——输出被截断时的断点续写、以及对照原文的查漏自检（`supplement_parse`）。后者对图文模组
此前**根本没机会生效**：没有原文可对照，它直接原样返回首轮结果。

OCR 前置把「认字」和「理解结构」拆开，图文模组于是能复用那条更强的链路。

## 需要留意的几处

- **取图口径不同**。视觉解析按体积降序取前 8 张（地图通常是最大那张）；OCR 前置改成**保持页序**、
  上限 60 页（`OCR_MAX_PAGES`）。扫描件一页一张图，按体积挑等于随机丢页还打乱顺序。
- **并发闸**。OCR 逐张独立调用，并发上限 3（`module_ocr.MAX_CONCURRENCY`）。本项目此前没有任何
  视觉/生图调用的并发控制，一次几十张全发出去容易被限流。
- **成本**。一本 40 页的扫描件 = 40 次视觉调用。跑之前心里有数。
- **fail-open**。单页失败只丢那一页；一页都没认出来（比如没配视觉模型）会回落到原来的图片路径，
  不会让开关把本来能解析的模组变成解析不了。
